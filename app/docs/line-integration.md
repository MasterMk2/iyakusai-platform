# LINE 連携（統合受信箱・模擬）

メールと LINE を同じ受信箱画面で扱い、担当・状態・内部メモ・履歴を付け、権限のある担当者が手動で返信できるようにする準備版。
送信の詳細な状態遷移は [LINE 返信契約](line-reply-contract.md) を参照する。

## 0. 委員会の公式LINE（2026-10-28 追加）

委員会の受信箱（Discord ログイン・`SMM_MAIL_CONFIG`）では、以下の節の模擬版の上に、実際の公式アカウントの受信と送信を足した。
下の 1〜9 節のうち「実際の LINE には接続しない」という記述は、模擬版（デモ・試験）についてのもの。

| 項目 | 内容 |
| --- | --- |
| 有効にする | `SMM_MAIL_CONFIG` と同じフォルダの `line.json`。無ければ LINE は無効。読めなければ LINE だけ無効にして受信箱は起動する（`src/server/line/oa-config.ts`）。 |
| 受信 | 既存の受け口（Webhook の署名を検証して記録する仕組み）の `GET /export?after=&limit=` を、読み出し用トークンで `pollSeconds`（既定 30 秒）ごとに読む第 2 の読み手。カーソルはアプリの保存ファイルに持つ。受け口の到着時刻から `settleSeconds`（既定 60 秒）たっていない記録は次の回に回す（表示名があとから足されるため）。形の読めない記録の手前で止まり、理由の分類だけを残す（`feed.ts`）。受け口は変更しない。 |
| 送信 | `line.json` の `"send"`（チャネルアクセストークンのファイル・`monthlyLimit` 既定 200・`allowGroups` 既定 false）があるときだけ。Messaging API のプッシュ、送信記録の再送キーを `X-Line-Retry-Key` に使う（`messaging-api.ts`）。応答の対応は [LINE 返信契約](line-reply-contract.md) の結果の分類のとおり。 |
| 月の上限 | 今月（日本時間）このアプリから送った通数（失敗を除く。グループは人数分）で数える。確認・送信・失敗の再試行のそれぞれで確かめる。確認の直前に、グループの人数と LINE 側の今月の通数を LINE から読む。 |
| 権限 | 受信箱の委員会の規則と同じ：臨時スタッフ以外の委員全員が閲覧と状態・担当・ラベルの変更、内部メモは編集の権限、送信は送信の権限（委員ごと・部局ごと）。権限管理者が `GET/PUT /api/line/admin/access` で扱う（`committee.ts`）。 |
| 保存 | `SMM_MAIL_DIR/line-state.json`（`line-state` の形式。読めないファイルは書き換えず LINE を無効のまま起動）。バックアップ（`ops/backup.ts`）に入る。 |
| 届かないもの | 公式アカウントの管理画面・アプリから送った返信（Webhook に来ない）。グループ名（受け口が持たない。ID の末尾で表示）。 |

## 1. 位置づけ

| 区分 | 内容 |
| --- | --- |
| 確認済みの利用者要件（CONFIRMED） | 統合受信箱での LINE の閲覧・担当・状態・内部メモに加え、**統合受信箱からの手動返信**が承認された（2026-10-09）。 |
| 実装済み（コードとテスト） | 合成データとモック接続での統合受信箱、アカウント単位の権限、正規化・重複排除・送信取消、確認付きの手動返信（模擬送信のみ）。 |
| 提案（PROPOSED） | 下の表の既定値（確認の有効期限、再送の安全期間、送信方法など）、受け取り経路の形、権限の初期値。 |
| 承認が必要（APPROVAL-REQUIRED） | 実際のチャネル・公式アカウント・アクセストークン、実送信アダプター、料金プランと通数、受け取り経路の配備、保存期間、本番の権限表、旧履歴の取り込み（後述の LN01〜LN09）。 |

このリポジトリは実際の LINE・グループ・Discord には一切接続しない。実在のメッセージ・添付・受信者 ID・認証情報も含まない。
既存の受け取り口（Webhook 受信と署名検証を行っている既存の仕組み）は変更・移設・再起動していない。

## 2. 構成

```text
既存の受け取り口（署名を検証）──正規化した封筒（line-event/v1）──┐
旧履歴のエクスポート（スナップショット行・ミラー行）─────────────┤→ 取り込み（ingest.ts：重複・競合・送信取消）
                                                                  ↓
ブラウザ → Fastify API → アカウント単位の ACL（line/access.ts）→ 参照・対応情報・返信（line/queries.ts, triage.ts, reply.ts）
                                                                  ↓
                         LINE 専用 JSON（*.line.json、kind=smm-line-state, schemaVersion=1）
                                                                  ↓（確認済みの送信意図だけ）
                                         LinePushConnector（模擬のみ。実アダプターは存在しない）
```

| ファイル | 責務 |
| --- | --- |
| `src/shared/line.ts` | LINE と統合受信箱の API 型。外部 ID・再送キー・確認値のハッシュは含めない。 |
| `src/server/line/normalize.ts` | 2 種類の入力アダプター（イベント封筒、旧履歴）。I/O なし。 |
| `src/server/line/ingest.ts` | 取り込み。重複・競合・送信取消の墓標・参加/友だち状態の観測。 |
| `src/server/line/access.ts` | アカウント単位の閲覧・編集・返信の判定。 |
| `src/server/line/queries.ts`、`triage.ts` | 一覧・詳細・件数・ラベル、担当・状態・メモ、権限管理。 |
| `src/server/line/reply.ts` | 下書き・確認・送信意図・結果・再試行の状態機械。 |
| `src/server/line/connector.ts` | 送信の境界と模擬コネクター。 |
| `src/server/line/store.ts` | 原子的な置き換え保存、種類・版の検証。 |
| `src/server/domain/inbox.ts` | メールと LINE の統合一覧（各 ACL の後で絞り込み・件数・ページ分割）。 |
| `src/server/http/line-routes.ts` | API とデモ専用の操作。 |

## 3. データと保存

- LINE のデータはメールの状態ファイルとは**別のファイル**に保存する。メールの状態（`schemaVersion: 1`）は変更しておらず、移行は不要。
- LINE ファイルは `kind: "smm-line-state"` と `schemaVersion: 1` を必須とし、それ以外（メールの状態、将来の版、壊れた JSON）は不正として扱う。
  trusted-proxy モードでは不正なファイルで起動を拒否し、ファイルを変更しない（バックアップから戻す）。デモモードは従来どおり合成データで置き換える。
- 書き込みは「一時ファイルに書いて置き換え」。更新は複製に対して行い、保存に成功してから置き換えるため、保存に失敗すると状態は変わらない。
- 設定：`SMM_LINE_MODE`（`off` / `mock`）と `SMM_LINE_DATA_FILE`。デモモードは既定で `mock`（メールのデータファイル名から `*.line.json` を作る）。
  trusted-proxy モードは既定で `off`。`mock` にするには専用の `SMM_LINE_DATA_FILE` が必須で、メールのファイルと同じ場所は拒否する。
  既存の運用中の試験環境に LINE のデータが混ざらない。`mock` 以外の値（実送信など）は存在しない。

| 概念 | 内容 |
| --- | --- |
| LineAccount | アプリ内の LINE アカウント。`official_account`（公式アカウント）か `legacy_archive`（旧履歴・閲覧専用）。`destination`（ボットのユーザー ID）は封筒の結び付けにだけ使い、API では返さない。 |
| LineConversation | (アカウント, 送信先の種類, 送信先 ID) で一意。`messaging_api`（user / group / room）か `legacy_chat`。対応情報・メモ・履歴を持つ。 |
| LineMessage | (アカウント, 由来, メッセージ ID) で一意。内容は本文・未対応の種類・取得不可・送信取消のどれか。 |
| ProcessedEvent / Tombstone | イベント ID と内容の指紋、送信取消の墓標。 |
| LineGrant | 利用者 × アカウントの `read` / `edit` と、別の `reply`（返信）権限。 |
| ReplyDraft / ReplyConsent / OutboxIntent | 返信の下書き・確認・送信意図（[返信契約](line-reply-contract.md)）。 |

同じ外部 ID でもアカウントが違えば別の会話・別のメッセージになり、権限も別に判定する。
メール・LINE・アカウントをまたいで、名前・アドレス・ID で人物を結び付けない。

## 4. 受け取り（入力アダプター）

### 4.1 イベント封筒 `line-event/v1`（今後の受け取り経路の提案）

既存の受け取り口が署名を検証した**後**に、正規化した封筒を読み取り専用のエクスポート（耐久性のある送り出しキュー）としてこのアプリへ渡す形を提案する。
このアプリは Webhook のルートを持たず、生の Webhook・署名・「検証済み」フラグを受け取らない。

| 項目 | 内容 |
| --- | --- |
| `accountId` / `destination` | アプリのアカウントとボットのユーザー ID。両方が登録済みの公式アカウントに一致しない封筒は拒否。 |
| `webhookEventId` / `isRedelivery` / `timestamp` | 重複判定・再配送の識別・時刻。 |
| `source` | `user` / `group` / `room` と ID（`U`/`C`/`R` + 32 桁の 16 進）。名前やメールアドレスは ID として受け付けない。 |
| `type` | `message`（`text` と、内容を取り込まない画像等）、`unsend`、`follow`、`unfollow`、`join`、`leave`、`member_count`（受け取り口が観測した人数）。 |
| `cursor` | 受け取り口側のキュー位置（来歴）。 |
| `senderLabel` / `targetLabel` | 表示用の名前（任意）。識別には使わない。 |

封筒は厳格に検証し、未知の項目を含むものは拒否する。特に**応答トークン（replyToken）を含む封筒は拒否**し、保存も使用もしない。

### 4.2 旧履歴のエクスポート（閲覧専用）

旧スナップショット（チャット・メッセージ・送信者の行）と、正規化ミラー（1 行 1 メッセージ）の 2 形式に対応する正規化関数を用意した。
実際の旧データはこのリポジトリで読んでいない（合成の例だけ）。

- 生のペイロード列・添付の実体・全文索引は取り込まない。暗号化で本文がない行は「取得できませんでした」、画像等は「内容は取り込んでいません」と表示する。
- 旧履歴のチャット ID・送信者名は Messaging API の送信先ではない。`legacy_chat` として保存し、**返信は常に不可**。
- 旧履歴は過去のある時点の記録で、すべての履歴の再現や現在の状態を保証しない。

### 4.3 過去の履歴についての制約

Messaging API では、テキスト本文は受信時の Webhook でしか得られず、あとから本文や過去の履歴を取得する API はない
（[メッセージの受信](https://developers.line.biz/en/docs/messaging-api/receiving-messages/)）。
このため、受け取り経路ができる前の会話をすべて再現することはできない。

## 5. 重複・競合・順序・送信取消

| 状況 | 結果 |
| --- | --- |
| 同じ (アカウント, イベント ID) で同じ内容（再配送を含む） | 重複。何も変えない。 |
| 同じイベント ID で内容が違う | 競合。拒否し、何も変えない。 |
| 同じ (アカウント, メッセージ ID) を別イベントで受け取り、内容が違う | 競合。 |
| 送信取消 | 墓標を残し、本文を「送信取消」に置き換え、本文から作った指紋を消す。履歴・監査には安全な ID だけを残す。 |
| 送信取消の後の再配送・別イベント | 抑止。本文は戻らない。取消が先に届いた場合も同じ。 |
| 時刻が前後して届く | 表示は送信時刻順（同時刻は ID 順）。古い follow/unfollow・join/leave・人数は新しい観測を上書きしない。 |
| 未登録のアカウント・宛先不一致・不正な形式 | 拒否（件数だけ記録）。 |

検索・一覧・抜粋・エクスポートの元になる正規の記録から本文が消えるため、送信取消後は検索でも見つからない。

## 6. 権限

- 権限は**アカウント単位**で、メールの受信箱の権限とは独立。グループ所属やログインから閲覧・管理の権限は付与しない。
- `read`：閲覧。`edit`：担当・状態・ラベル・メモ。`reply`：手動返信（閲覧が必要、編集とは別）。
- 権限管理者は権限表を変更できるが、会話の内容は閲覧できず、自分に付与もできない。
- 無効化された利用者は LINE のすべての操作を拒否される。
- 一覧・検索・件数・ラベル候補・ページ分割は、各アカウントの ACL を適用した後の項目だけで計算する。未許可・不明な会話・送信記録は同じ 404。
- trusted-proxy モードで LINE を有効にした場合、初期データの返信権限はすべて無効（本番の既定は拒否）。付与は権限管理者の明示的な操作で、監査に残る。

## 7. 画面

- 統合一覧に「メール」「LINE」のバッジ、種類の絞り込み、内訳の件数。サイドバーに LINE アカウント（閲覧・返信の可否と未対応件数）。
- 会話の詳細：送信先の種類（1:1 / グループ / トークルーム / 旧履歴）と ID の末尾、時刻順の表示、内容のない項目の正直な表示、対応情報・メモ・履歴。
- 模擬モードであること、実際の LINE には送信されないことを常に表示する。「受付済み」は配信・既読を意味しないと明記し、「配信済み」とは表示しない。

## 8. 承認が必要な事項（LN01〜LN09）

| ID | 内容 |
| --- | --- |
| LN01 | 対象の公式アカウント・チャネルと、アプリ内アカウントとの対応（ボットのユーザー ID）。 |
| LN02 | 既存の受け取り口からの読み取り専用エクスポート（形式・耐久性・認証された経路・配備）。既存の受け取り口の変更は別承認。 |
| LN03 | 実送信アダプター（チャネルアクセストークンの保管・回転、HTTP クライアント、タイムアウト）。 |
| LN04 | 料金プラン・月間の通数・追加通数の可否と、送信してよい上限。このアプリは残り通数を照会しない。 |
| LN05 | グループ・トークルームへの送信（人数の観測方法、全員に届くことの扱い、費用）。既定は人数を確認できないものは閲覧のみ。 |
| LN06 | 本番の権限表（誰が閲覧・編集・返信できるか）と運用。 |
| LN07 | 旧履歴の取り込み可否・範囲・保存期間・削除。 |
| LN08 | 保存先（単一プロセスの JSON は本番用ではない）、バックアップ、本文・送信記録の保存期間。 |
| LN09 | 既定値（確認の有効期限 5 分、再送の安全期間 23 時間 50 分、本文 5000 文字、確認待ちの上限＝全体 100 件・1 人あたり 10 件）の確定。1 人あたりの上限は暫定値で、1 人の返信者が全体の枠を使い切って、ほかの返信者が 5 分間確認できなくなることを防ぐ。数えるのは期限内で未使用の本人の確認だけで、送信・下書きの破棄・同じ下書きの再確認・期限切れで枠は戻る。ほかの利用者の有効な確認は追い出さない。全体の 100 件は期限内の確認の記録（使用済みを含む）を数えるメモリの上限。 |

## 9. 参考（2026-10-09 確認、要旨）

- [メッセージの受信](https://developers.line.biz/en/docs/messaging-api/receiving-messages/)：本文は受信時の Webhook で受け取る。
- [応答メッセージ](https://developers.line.biz/en/reference/messaging-api/nojs#send-reply-message)：応答トークンは 1 回限りで、受信後すぐに使う必要がある。
- [プッシュメッセージ](https://developers.line.biz/en/reference/messaging-api/nojs#send-push-message)：送信できる相手の条件、再送キー、HTTP 200 は受付の意味。
- [料金](https://developers.line.biz/en/docs/messaging-api/pricing/)：プッシュは月間の通数に数えられ、応答は数えられない。
- [API 要求の再試行](https://developers.line.biz/en/docs/messaging-api/retrying-api-request/)：再送キーの有効期間と、受付済みの重複を示す 409。
