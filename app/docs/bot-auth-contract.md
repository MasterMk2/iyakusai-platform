# Bot 連携契約（ログインコードの DM 配送・提案）

既存 Discord Bot の実装者向けに、[グループ所属 + Bot DM ログイン](group-discord-auth.md)の配送境界を示す。
この契約はログイン側の設計だけから作った**提案（PROPOSED）**で、Bot のソースは参照していない。
Bot 側の変更、Intent・アプリ登録・権限・トークンの変更、実際の DM 送信はこのリポジトリでは行っていない（APPROVAL-REQUIRED）。

## 1. 役割分担

| 担当 | 責務 |
| --- | --- |
| ログインサービス | 利用資格・連携・内部利用者の確認、コード生成、ハッシュ保存、期限・回数・レート制限、セッション。 |
| Bot | 受け取った封筒の宛先が承認済みの連携から来たことを確認し、その 1 人へ定型の DM を 1 通だけ送り、結果を返す。 |

Bot は利用資格を判断しない。グループ全体への一斉送信、チャンネルへの投稿、宛先の変更・追加はしない。

## 2. 通信路（APPROVAL-REQUIRED・未決定）

- ローカルまたは内部ネットワークの、相互に認証された経路（例：相互 TLS、または承認済みの共有鍵による要求署名と時刻・再送の検査）。
  方式と鍵の作成・保管は未決定で、この準備版では作っていない。
- 公開インターネットに受け口を出さない。Bot のトークン・共有鍵・署名鍵をログ・監査・エラー応答に出さない。
- 準備版のログインサービスは `BotDelivery` という注入された関数を呼ぶだけで、HTTP 送信や認証情報を持たない。
  テストの配送先は合成の記録用の関数で、Discord との接続ではない。

## 3. 型付きメッセージ（提案）

要求（ログインサービス → Bot）：`LoginCodeEnvelope`（`src/server/login/types.ts`）

| 項目 | 型 | 内容 |
| --- | --- | --- |
| `kind` | `'login_code'` | 固定。 |
| `deliveryId` | `dl_` + 32 桁の 16 進 | 冪等キー。発行ごとに一意。 |
| `template` | `'login_code_v1'` | 文面は Bot 側の固定テンプレート。呼び出し側の文字列を本文に入れない。 |
| `recipient.discordUserId` | 数字 17〜20 桁 | 承認済みの連携に登録された安定 ID。表示名・ユーザー名ではない。 |
| `recipient.linkId` / `linkVersion` | 文字列 / 整数 | Bot が承認済み連携と照合するための参照。 |
| `code` | 数字（既定 8 桁） | 機密。送信後は保持・記録しない。 |
| `expiresAt` | ISO 8601 | 有効期限。 |
| `context.serviceLabel` / `requestedAt` | 文字列 / ISO 8601 | DM に示す一般的な文脈だけ。メールアドレス・IP・ブラウザ情報は含めない。 |

応答（Bot → ログインサービス）：`DeliveryAck`

```ts
{ deliveryId: string; status: 'delivered' }
{ deliveryId: string; status: 'failed'; reason: 'dm_closed' | 'blocked' | 'rate_limited' | 'timeout' | 'recipient_mismatch' | 'unavailable' }
```

## 4. Bot が守ること

1. **宛先の確認**：`recipient.discordUserId` が、Bot 側でも参照できる承認済み連携（`linkId`・`linkVersion`）と一致することを確認する。
   一致しない・連携が無効なら送らずに `recipient_mismatch` を返す。要求に書かれた ID だけを根拠に任意の人へ送らない。
2. **本人が開始した送信だけ**：ログイン要求に応じた登録者本人への DM だけ。グループ・チャンネル・複数人へは送らない。
3. **文面の安全性**：固定テンプレートだけを使い、`allowed_mentions` は空（`parse: []`）にしてメンションを無効化する。
   埋め込み・リンク・ボタンの URL を入れない（リンクの差し込みを防ぐ）。コードは文字として表示する。
4. **冪等性**：同じ `deliveryId` は最大 1 通。再送されたら前回の結果を返す。重複排除の記録には `deliveryId` と結果だけを
   有効期限まで残し、コードや本文は残さない。
5. **失敗の扱い**：DM 不可（受信拒否・共通サーバーなし・ブロック）、Discord の 429（`retry_after` に従い、コードの期限内で 1 回まで）、
   タイムアウト、障害は `failed` と理由で返す。ログイン側は失敗・時間切れ（既定 10 秒）・別の `deliveryId` の応答でコードを破棄する。
   遅れて `delivered` を返してもコードは復活しない。
6. **記録**：コード・DM 本文・トークン・認証情報をログに出さない。記録するのは `deliveryId`、結果、時刻程度に限る。

DM 文面の提案（日本語）：

> 共有メール管理（{serviceLabel}）のログインコード：**{code}**（{有効期限} まで有効、1 回限り）
> {requestedAt} の要求です。ご自身でログインを要求した場合にだけ入力してください。このコードを他の人に転送・共有しないでください。
> 心当たりがない場合は入力せず、管理者に連絡してください。

## 5. 追加の確認ボタン等を設ける場合（任意・APPROVAL-REQUIRED）

DM に「このログインを承認」等のボタンを付ける場合は、操作者を Discord から届いた正規の Interaction（署名検証済み）の
利用者 ID で確認し、要求本体に書かれた利用者 ID を使わない。ボタンの状態は同じ Web の挑戦（`deliveryId`）に結び付け、
別の挑戦・別の人の操作として扱わない。この準備版では実装していない。

## 6. 前提条件のチェックリスト（すべて未完了）

- [ ] 対象グループの安定 ID と組織 ID が設定されている（L01。利用者の範囲＝委員会グループの実効メンバーは確認済み）。
- [ ] 実効メンバーシップの提供元・権限・スコープが承認されている（L02）。Bot は所属を判断しない。
- [ ] 承認済み連携の初期登録根拠と、Bot から連携を照合する読み取り手段が決まっている（L03）。
- [ ] 相互認証された内部通信路と鍵の作成・保管が承認されている（L05）。
- [ ] Bot の既存の Intent・権限で DM を送れることを、変更なしで確認できている（変更が必要なら別途承認）。
- [ ] 429・DM 不可・タイムアウト時の挙動と、`deliveryId` の重複排除の保持期間が決まっている。
- [ ] DM 文面と言語が承認されている（L07）。
- [ ] 最初の運用は合成データに限ることが合意されている（L08）。
