# グループ所属 + 既存 Bot の DM によるログイン（準備版）

この文書は、登録済みグループのメールアドレスで利用資格を確認し、既存の Discord Bot の DM で
短時間・1 回限りのコードを届けてログインする方式の**準備段階の設計**を示す。

> 2026-10-10 更新: このコアは `SMM_AUTH_MODE=account`（本番構成）と `account-mock`（模擬構成）に接続し、コードは「本人がパスワードを設定する」ための一回限りの確認に使う方式になった。
> 実プロバイダーは未接続。現在の設計は [統合設計](unified-integration.md) を正とする。下記の「アプリ本体に未接続」は当時の記述。

- **確認済み（CONFIRMED）**：このリポジトリのコードとテストで確認できる事項。
- **提案（PROPOSED）**：既定値や運用方法の案。変更可能で、承認済みではない。
- **承認が必要（APPROVAL-REQUIRED）**：実施前に対象と影響を示して明示的な承認が必要な事項。

**本番の認証は配備されていない。** 認証コアは `src/server/main.ts` と `buildApp` のどちらにも接続しておらず、
起動設定（`SMM_AUTH_MODE`）にも新しいモードはない（`demo` / `trusted-proxy` 以外は起動拒否のまま）。
グループの読み取り、Bot への配送、保存先はすべてテストで注入する合成の提供元だけで、実在の
グループ・アカウント・Discord・ディレクトリには一切接続していない。

## 1. 要求と方針

| 区分 | 内容 |
| --- | --- |
| 要求（2026-10-09） | 登録済みグループのメールアドレスとパスワードで利用資格を確認し、既存 Bot の DM でパスワードを届ける。 |
| 提案（親タスク） | 固定・再利用のパスワードではなく、短時間・1 回限りのコードにする。この準備版はその案で実装した。 |
| 確認済み（2026-10-09） | 「全員」は委員会の全メンバー。対象は設定したグループの実効メンバー（直接・入れ子・組織の全利用者）。§4。 |
| 未決定 | 実効メンバーシップの提供元・権限・スコープ（後述）、連携の初期登録方法、保存期間、保存先・秘密情報・Bot との通信方式、起動への接続。 |

Discord の DM で届けるコードは「その Discord アカウントを操作できる」ことの証拠にすぎない。
フィッシング耐性のある多要素認証ではなく、NIST SP 800-63B の認証器・保証レベル（AAL）を満たすとは主張しない。
最初の実運用は合成データに限定し、実データを扱う前に認証の保証水準を別途承認する（APPROVAL-REQUIRED）。

## 2. 構成と信頼境界（CONFIRMED：準備版のコード）

```text
ブラウザ ──(HTTPS, __Host- Cookie)──▶ ログイン HTTP ハーネス（http.ts, ローカル専用・未配線）
                                         │
                                         ▼
                                   LoginService（service.ts）── 監査（仮名化イベントのみ）
                                         │  非同期・上限付きの配送キュー
          ┌──────────────────────────────┼───────────────────────────────┐
          ▼                              ▼                               ▼
 IdentityLinkDirectory          GroupMembershipReader                 BotDelivery
 （運用者管理の連携・読み取り）    （所属の読み取りのみ）                   （注入された呼び出し）
          ▼
 PrincipalDirectory（既存の内部利用者。権限はここだけから決まる）
```

| ファイル | 内容 |
| --- | --- |
| `src/server/login/types.ts` | 提供元インターフェース、配送封筒、監査イベント、方針の既定値と許容範囲。 |
| `src/server/login/service.ts` | 要求・非同期配送・検証・セッション・取消。構成の検証（不備は `ConfigError` で構築拒否）。 |
| `src/server/login/memory-store.ts` | 単一プロセスのメモリ参照ストア（テスト専用。再起動で全消失）。上限付きの挑戦・セッション・レート計数。 |
| `src/server/login/crypto.ts` | Node の `crypto` だけを使うコード生成・ハッシュ・定数時間比較。固定の秘密値は持たない。 |
| `src/server/login/http.ts` | Cookie・Host・Origin・CSRF・`no-store` を示すローカル専用ハーネス。`app.inject` のテストだけが使う。 |

信頼するもの：運用者が登録した連携（IdentityLink）、権威ある所属の読み取り結果、既存の内部利用者、
運用者が定義した接続元キー（例：TCP ソケットやエッジの確認済み値）。
信頼しないもの：ブラウザが送る Discord ID・役割・グループ・検証済みフラグ、転送系ヘッダー（`X-Forwarded-For` 等）、
表示名・ユーザー名、DM での自己申告（`/link` 等）。リクエスト本体は `strictObject` で未知の項目を 400 にする。

## 3. 流れと状態

1. ブラウザが `POST /api/login/challenge { email }` を送る。
2. サーバーは形式だけを確認し、**対象にかかわらず同じ** 202 応答（`challengeId`、有効秒数、固定文言）を返す。
   ブラウザ結合用の秘密値（256 ビット）は `__Host-smm_login` Cookie だけに入れ、JSON には含めない。
3. 応答後に配送キューで、対象ごとの配送上限 → 連携 → 内部利用者 → 所属を順に確認する。
4. すべて満たした場合だけ、連携済みの Discord ID 宛てに Bot がコードを DM で送る。
   Bot が `delivered` を返すまでコードは使えない。失敗・時間切れ・別 ID の応答ではコードを破棄する。
5. 同じブラウザが `POST /api/login/verify { challengeId, code }` を送る（結合 Cookie 必須）。
6. コードが一致したら**同期的に消費**（以後は再利用不可）し、その後で連携の版・内部利用者・所属を再確認する。
7. 新しいセッショントークン（256 ビット）を発行し、`__Host-smm_session` Cookie に入れる。役割・権限は既存の内部利用者から決まる。
8. 以後の要求ごとに連携・内部利用者・所属を再確認する（キャッシュなし）。

挑戦（challenge）の状態：

| 状態 | 意味 | 遷移 |
| --- | --- | --- |
| `open`（コードなし） | 作成直後、資格なし、配送失敗、レート上限 | 配送成功で「コードあり」へ。期限で失効。 |
| `open`（コードあり・未確認） | 生成済みで Bot の確認待ち | 確認で「使用可」、失敗で「コードなし」。 |
| `open`（使用可） | DM 配送済み | 一致で `consumed`、5 回失敗で `dead`、再送で新コードに置換。 |
| `consumed` | 使用済み | 再提出は `replay` として失敗。 |
| `dead` | 失敗上限・取消イベント | 何も受け付けない。 |

## 4. 利用資格（グループの実効メンバー）

**対象者（CONFIRMED：2026-10-09 の利用者の確認）**：「全員」は委員会の全メンバーを指し、ログインの対象は
設定したグループの**実効メンバー**（直接の所属、入れ子のグループ経由の所属、管理された「組織の全利用者」項目による所属）。
直接所属の利用者だけに絞らず、組織の全利用者の項目も外さない。以前の「直接所属の利用者だけ」という記述はこれで置き換える。
実際のグループのアドレス・ID と現在の構成員は Git の外で管理し、このリポジトリには置かない。

`GroupMembershipReader.lookup(groupId, memberKey)` は 1 人分の実効メンバーシップの観測
（`kind: 'effective_membership/v1'`）を返す読み取り専用の境界。資格ありとするのは次をすべて満たす場合だけ
（CONFIRMED：合成の提供元を注入したテストで各ケースを確認）。

- 観測の形式が `effective_membership/v1`（それ以外、例えば直接所属の真偽だけを返す旧形式は `membership_unsupported`）。
- `groupId` が設定したグループ ID と一致し、`memberKey` が連携のものと一致する（別グループ・別人は拒否）。
- `resolution` が `complete`。隠れた子グループ・ページ分割の途中・探索の上限・循環で決定的な答えがない場合
  （`incomplete`・`limit_exceeded`・`cycle`）は `membership_unresolved`、権限なし・利用不可（`forbidden`・`unavailable`）は `provider_failure`。
- `effectiveMember` が `true`（`false` は `not_member`、`unknown` は `membership_unresolved`）。
- `subjectType` が `user`、かつ `subjectState` が `active`。グループや組織（顧客）の項目そのものは利用者ではなく、
  連携が指していてもセッションを作らない。招待中・停止・アーカイブ・削除・不明は拒否。
- `provenance`（`direct`・`nested`・`organization`）が空でなく重複がない。どれでも資格は同じで、権限は何も変わらない。
- `organization` を含む場合は、観測の `organizationId` がサーバーに設定した組織 ID（`LoginServiceOptions.organizationId`）と一致する。
  未設定・別の組織は `wrong_organization`。組織の項目は「この組織の全利用者」であって、任意のメールを許す指定ではない。
  `organization` を含まないのに `organizationId` がある観測は矛盾として拒否する。
  `direct`・`nested` と `organization` が同時にある場合も同じで、組織 ID が未設定・不一致なら他の経路があっても拒否する
  （矛盾した根拠を安全側に扱う。CONFIRMED：直接所属＋組織の合成テストで、正しい組織 ID なら許可、不一致・未設定なら拒否）。
  **設定上の前提**：対象グループが管理された「組織の全利用者」の項目を含む場合、起動・接続の前に実際のサーバー組織 ID の設定が必須。
  未設定は「根拠の欠落」であって拒否になり、確認済みの対象者（実効メンバー全員）を狭める選択肢として使ってはならない。
  実際の組織 ID・グループのアドレスは Git の外で管理する（このリポジトリの例は予約ドメイン・架空の ID だけ）。
- `groupRevision` が空でなく、`observedAt` が現在から 30 秒以内（PROPOSED。未来の時刻も拒否）。
- 例外・タイムアウト（既定 5 秒）は `provider_failure` として拒否。

外部（組織のドメイン外）の利用者を新たなドメイン制限で自動的に除外しない。権威ある実効メンバーの答えと検証済みの連携が
そろえば、同じ契約で判断する。逆に、メールアドレスのドメインやブラウザの申告（経路・由来・グループ・組織）から所属を推定しない。
サーバーは注入された提供元だけを信頼し、ログイン要求の本体は未知の項目を 400 にする。
所属は「利用資格」を示すだけで、メールアドレスの所有や Discord アカウントの連携を証明しない。
**グループ所属 ≠ 受信箱の閲覧権限**：ログイン後の閲覧・編集は既存の受信箱・LINE の ACL と内部利用者の設定だけで決まり、
入れ子・組織経由の所属や、グループのオーナー・マネージャーであることから管理者・閲覧権限は生じない（`canManageAccess` は内部利用者の値）。
管理者でも内容は読めない（既存の挙動。テストで確認）。

提供元（APPROVAL-REQUIRED・未決定）：実際にどの読み取り手段・スコープ・管理者権限で、入れ子と組織の全利用者を含む
実効メンバーシップを権威ある形で答えられるかは確認していない。直接所属だけを答える API の結果を推移的とみなしてはならず、
アダプターは解決できなかった場合に `incomplete`・`unknown` を返す必要がある。一般向け（コンシューマー）の Google グループは自動的には対象にならない。
この準備版は Google の API アダプターを作っていない。既存の適法な読み取り手段が提供された場合はそれを優先し、
ドメイン全体の委任・スコープ追加・新しい認証情報はこちらで作らない。テストの提供元は合成のグループ構成を探索するモックで、
実際の構成員や権限を確認したものではない。

## 5. メール・Discord・内部利用者の対応（連携）

`IdentityLink` は運用者が管理する記録で、正規化したメール（`emailVerified: true`）、Discord の数値 ID、
所属照会用の `memberKey`、既存の内部利用者 ID、`version`、`status`、根拠（`evidence`）を持つ。

- 照合は正規化後（前後空白の除去と ASCII 小文字化だけ）の完全一致。別名・`+` 付き・ドット違い・別ドメインは一致しない。
  ディレクトリが別名を解決して別人の連携を返しても、連携のメールが要求と一致しなければ拒否する。
- 表示名・ユーザー名・ブラウザ入力・DM での自己申告では連携を作れない。コアには連携を作る操作がない。
- `version` の変化、`revoked`、内部利用者の無効化は、発行済みのコードと既存セッションを無効にする。
- 初期登録（APPROVAL-REQUIRED・未解決）：次のいずれかを運用者が選び承認するまで本番では使えない。
  (a) 独立に確認済みの名簿、(b) 運用者の確認・証明、(c) 別途承認された両アカウントの操作確認。
  構成の `acceptedLinkEvidence` が空なら構築を拒否する（テストは `operator_attestation` だけを許可）。

## 6. 公開応答と列挙対策

| 状況 | 公開応答 |
| --- | --- |
| 登録済み・未登録・未検証・所属なし・配送拒否・対象ごとの配送上限 | すべて 202 で同じ項目・文言・Cookie。違いは監査だけに残る。 |
| 接続元・全体の要求量の上限（所属と無関係に判定） | 429 `rate_limited` |
| 挑戦の保存上限 | 503 `unavailable`（全体の容量の問題で対象に依存しない） |
| メール形式の誤り、未知の項目 | 400 |
| 検証の失敗（誤り・期限切れ・別ブラウザ・再利用・失敗上限・資格喪失） | すべて 401 `login_failed` |

時間差について（正直な限界）：所属確認と DM は応答後の非同期キューで行うため、HTTP 応答の時間に所属・配送の待ち時間は
含まれない。同期部分は入力検証、HMAC、メモリ上の計数と記録だけで、対象による分岐はない。
ただし CPU やキューの混雑による全体の遅延、DM が届くかどうかそのもの（本人の Discord を見られる人には分かる）は
隠せない。Bot・ディレクトリの応答時間が別の経路（例：Bot の公開ステータス）で観測できる場合も対象外。

## 7. 既定値（PROPOSED。`LoginPolicy` で範囲内に限り変更可能）

| 項目 | 既定値 | 許容範囲（逸脱で構築拒否） |
| --- | --- | --- |
| コード | 数字 8 桁（CSPRNG の `randomInt`） | 6〜10 桁 |
| コード有効期間 / 挑戦の寿命 | 5 分 / 15 分 | 1〜10 分 / 1〜30 分 |
| 挑戦ごとの失敗上限 | 5 回（超えると正しいコードも不可） | 1〜10 |
| アカウント単位の失敗上限 | 15 分で 5 回。再送・新しい挑戦でも減らない | 1〜20 回 |
| 対象ごとの DM | 60 秒に 1 通、15 分に 3 通。未登録の対象も同じ計数 | — |
| 接続元 | 要求 10 回・検証 30 回 / 15 分 | — |
| 全体 | 要求 300 回 / 分 | — |
| セッション | 無操作 30 分、絶対 8 時間 | 無操作 ≤ 絶対 |
| 所属の鮮度 | 30 秒以内の観測 | 0〜5 分 |
| 提供元・配送のタイムアウト | 5 秒・10 秒 | — |
| メモリ上限 | 挑戦 10,000、セッション 10,000、計数キー 20,000、キュー 100、並列 4 | — |

- 接続元キーは運用者が定義した信頼できる値（TCP ソケット、確認済みエッジの値）から作る。ブラウザが送る IP・利用者ヘッダーは使わない。
  キーがない場合は拒否する。保存するのは鍵付きハッシュだけ。
- 計数のキー領域が満杯のときは、期限切れのキーだけを消す。生きている（制限中の）キーは消さず、新しい要求を拒否する。
- 既知の制約：攻撃者が他人のメールアドレスで要求を繰り返すと、その人への DM が上限で止まり、
  誤ったコードを 5 回送るとその人のアカウント単位の失敗上限に達する（15 分のサービス妨害）。推測防止を優先した結果。

## 8. 再送・重複・取消

- 同じ挑戦での再送（`/api/login/resend`、結合 Cookie 必須）は新しいコードを発行し、古いコードを無効にする。
  配送中の再送はまとめて 1 回にする。対象ごとの上限内でなければ何もしない（古いコードは有効のまま）。
- メールアドレスだけの新しい要求は別の挑戦を作るだけで、他のブラウザの挑戦や既存セッションを取り消さない。
- 別ブラウザ（結合 Cookie なし・不一致・重複）からは正しいコードでも失敗する。
- 同じコードの同時提出は 1 件だけが成功する（同期的な消費。テストで 10 並列を確認）。
- 配送の冪等性：`deliveryId` ごとに Bot は最大 1 通だけ送る。遅れて届いた確認・別 ID の確認・再度の確認で
  コードが復活したり、失敗回数が戻ったりしない。
- 取消イベント `handleDirectoryEvent`：`membership_removed`（memberKey）、`link_changed`（linkId）、
  `principal_disabled`（principalId）で、該当するセッションと未使用の挑戦を即時に無効にする。
  確認中の検証・配送もイベント後はセッション・コードを作らない。
- 要求ごとの再確認で、所属の喪失・連携の変更・内部利用者の無効化・提供元の障害が分かった場合はセッションを削除する。
  提供元の障害で全員がログアウトされる点は、フェイルクローズを優先した既知の挙動。
- 直接・入れ子・組織のどの経路の喪失でも、実効メンバーでなくなれば次の要求でセッションを削除する。
  経路が変わっても実効メンバーのままなら（例：入れ子から直接へ、組織から入れ子へ）喪失とは扱わず、セッションは続く。
  セッションは経路・由来・グループの版を保存しないため、版の変化だけでの回転（強制再ログイン）はしない。
  これは「資格の有無だけを要求ごとに確認する」選択で、経路の変化を監査したい場合は提供元側の記録に頼る。
  入れ子・組織の変化は特定の memberKey に結び付かないことが多いので、`membership_removed` イベントではなく要求ごとの再確認で反映する。

所属・連携の変化の反映（SLA の提案）：キャッシュなしのため、要求ごとの確認で即時に拒否する。
変化を能動的に知らせるイベント源（Directory の変更通知、定期ポーリング、運用者の操作）は未決定（APPROVAL-REQUIRED）。
イベント源がない間は、次の要求での拒否と無操作 30 分・絶対 8 時間が上限になる。
キャッシュを導入する場合は、最大遅延（例：キャッシュ有効期間 + 観測の鮮度）を明記し、期限切れ時は拒否する。

## 9. コード・セッション・秘密情報の扱い

- コードは挑戦ごとのソルトと注入されたペッパーによる HMAC-SHA256（挑戦 ID と世代を含む）だけを保存し、定数時間で比較する。
- セッショントークンとブラウザ結合値は SHA-256 だけを保存する。対象メールは鍵付きハッシュだけを保存する。
- ペッパーは 32 バイト以上の注入値が必須（全バイト同一は拒否）。テストは使い捨ての値を注入する。
  本番用のペッパー・パスワード・鍵はリポジトリに置かず、作成もしていない（保管方法は APPROVAL-REQUIRED）。
- コード・秘密値・トークンを URL、`localStorage`、コンソール、監査、公開 JSON に入れない。ハーネスはクエリ文字列を 400 にする。
- ログイン時に既存のセッション Cookie を示された場合は失効させ、常に新しいトークンを発行する（セッション固定対策）。
- ログアウトはサーバー側でセッションを削除し、Cookie を消す。

## 10. HTTP の提案（ハーネスで確認済み）

| 項目 | 内容 |
| --- | --- |
| Cookie | `__Host-smm_login`（結合値, 15 分）と `__Host-smm_session`（8 時間）。`Secure; HttpOnly; SameSite=Strict; Path=/`、`Domain` なし。同名 Cookie の重複は拒否。 |
| Host | 設定した公開ホストと完全一致（421）。公開オリジンは既存の `parsePublicOrigin` で https・正規形を必須にする。 |
| 変更要求 | 公開オリジンと完全一致する `Origin`、`Sec-Fetch-Site` は `same-origin`（ある場合）、`X-SMM-Login: 1`、JSON 本体。満たさなければ 403。 |
| 応答ヘッダー | `Cache-Control: no-store`、`Pragma: no-cache`、`Referrer-Policy: no-referrer`、`X-Frame-Options: DENY`、制限的な CSP（`default-src 'none'` ほか）。 |

要求・応答の項目（PROPOSED）：

| 経路 | 要求 | 成功 | 失敗 |
| --- | --- | --- | --- |
| `POST /api/login/challenge` | `{ email }` | 202 `{ status: 'accepted', challengeId, expiresInSeconds, message }` + 結合 Cookie | 400 / 429 / 503 |
| `POST /api/login/resend` | `{ challengeId }` + 結合 Cookie | 202（同じ形） | 401 `login_failed` / 429 |
| `POST /api/login/verify` | `{ challengeId, code }` + 結合 Cookie | 200 `{ user }` + セッション Cookie、結合 Cookie 削除 | 401 `login_failed` / 429 / 503 |
| `GET /api/login/session` | セッション Cookie | 200 `{ user }` | 401（Cookie 削除） |
| `POST /api/login/logout` | `{}` | 200 `{ ok: true }` | — |

`user` は既存の `SessionUser`（`id`、`displayName`、`roleLabel`、`canManageAccess`）。

## 11. 監査

監査イベントは `type`・`at`・`subjectRef`（対象メールの鍵付きハッシュ 16 桁）・`challengeRef`（12 桁）・`reason` だけ。
メールアドレス、IP、コード、トークン、結合値、DM 本文、Discord ID は含めない（テストで確認）。
運用者は期限切れ・誤り・拒否理由・再利用・配送失敗・ログイン・ログアウト・取消・上限到達を区別できるが、
公開応答からは区別できない。監査の失敗は認証の結果を変えない（許可には働かない）。

## 12. 失敗時の安全側の動作

- 提供元・配送・監査・ストアの設定がない、グループ ID・組織 ID（指定した場合）が不正、承認済みの根拠がない、ペッパーが弱い、
  方針が範囲外、ストアの承認値がない場合は `LoginService` を構築できない（認証もセッションも作れない）。
- 組織の全利用者の項目を含むグループで組織 ID が未設定・不一致の場合、構築はできても組織の根拠を含む観測はすべて
  `wrong_organization` で拒否される（直接・入れ子の経路が同時にあっても拒否）。これは設定漏れであり、対象者を絞る手段ではない。
  起動・接続前に実際の組織 ID を Git の外で設定することが前提（未実施。他の前提条件も未充足）。
- ハーネスは `app.inject` のテストだけで使い、待ち受けを開始する入口はない。未設定のサービスをネットワークへ出さない。
- メモリ参照ストアは再起動で全消失し、既存の挑戦・セッションはすべて拒否される（テストで確認）。永続化された本番用とは扱わない。
