# 共通入口・受信案件からのタスク作成・アカウント認証（統合設計）

この文書は、共有メール管理（本リポジトリ）を **共通の Web 入口** とし、委員会タスク管理（discord-task-manager）を
**唯一のタスク保存先** として結合した構成を示す。実装済みの合成データでの統合、本番用に用意した契約、
まだ接続していない実プロバイダー、未決事項を区別して記す。配置は [配置](../../docs/deployment.md) を参照。

## 1. 実装状況の区別

| 対象 | 状態 | 内容 |
| --- | --- | --- |
| 共通画面（タスク／受信箱（メール・LINE）／設定） | 実装済み | 日本語ナビゲーション、直リンク（`#/tasks?ws=…&task=…`、`#/settings` など）と再読込、読み込み中・空・失敗・再試行・キャンセル表示 |
| Task ゲートウェイ（サーバー間） | 実装済み・合成データで検証 | 署名付き要求で Task サービスの保護 API を呼ぶ。タスクの複製や二重書込はしない |
| 受信案件（メール・LINE）→ 担当付きタスク | 実装済み・合成データで検証 | 元案件の読取権限とタスク作成権限の両方を確認。本文・添付・件名は自動転記しない |
| Discord 連携 | 契約と模擬送信のみ | Task サービス側の署名付き Discord コマンド API と対応表。実 Discord・既存 Bot には未接続 |
| アカウント認証（DM コード → 本人がパスワード設定 → 通常ログイン） | 実装済み・模擬プロバイダーで検証 | production 構成は本人 bridge（運用者提供）への署名付きアダプター（既定）と、明示 opt-in の direct 構成（6.5）。実 bridge・実 Directory は未接続 |
| direct 構成（Directory 読み取り + 本人紐付けレジストリ） | 実装済み・合成 Directory で検証（POSIX のみ） | 実 Google Directory への接続は未検証。資格情報のライフサイクル・レジストリの取り込み・DM 送信が未実装で、実運用の阻害要因（6.5） |
| メール取込・LINE | 模擬のみ（従来どおり） | 実メールボックス・実 LINE には接続しない |

「実接続」は存在しない。実メール取込・実 LINE・既存 Bot・本人 bridge（Google Workspace の実効会員照会と Discord DM）はすべて **未接続** で、
下記 6 章の非秘密の契約と運用者の設定が必要。

## 2. 構成

```text
ブラウザ ──HTTPS──> リバースプロキシ ──> 共通 Web（本リポジトリ, Fastify）
                                          ├─ 受信箱 API（メール・LINE の受信箱／アカウント単位 ACL）
                                          ├─ アカウント認証（LoginService + 永続ストア）──署名──> 本人 bridge（運用者提供・未接続）
                                          └─ Task ゲートウェイ ──署名 svc-auth/v1──> Task サービス（保護モード・内部専用）
                                                                                          ↑
                                                       Discord 連携 Bot（運用者提供・未接続）──署名──┘
```

- **唯一のタスク保存先** は Task サービスの保存ファイル。共通 Web はタスクを保存しない。Web と Discord は同じ
  `TaskService` の操作・タスク ID・版（version）・委員会権限・変更履歴を使う。
- 共通 Web が保持するのは「どのタスクがどの受信案件から作られたか」の関連付け（`*.task-links.json`）と、
  受信案件からの作成要求の操作記録だけ。Task サービスは元案件について何も保存しない。
- 本人の対応付け（**タスク本人対応表**）: 認証済みの本人（共通 Web の利用者 ID = 認証の principal）→ Task 利用者 ID。
  運用者が管理するファイルで、メールのドメインや表示名、ブラウザの申告から推測しない。対応がない利用者はタスク機能を使えない。

主なファイル:

| 層 | ファイル |
| --- | --- |
| 署名（svc-auth/v1） | `src/server/tasks/signing.ts` |
| Task クライアント・本人対応表・関連付け保存 | `src/server/tasks/client.ts`、`bridge.ts`、`links.ts` |
| ゲートウェイ API・受信案件からの作成・元案件表示 | `src/server/tasks/routes.ts` |
| アカウント認証（コア） | `src/server/login/service.ts`、`password.ts`、`memory-store.ts`、`file-store.ts` |
| アカウント認証（HTTP・構成） | `src/server/account/http.ts`、`bridge-client.ts`（本番）、`mock-providers.ts`（模擬） |
| 設定・起動 | `src/server/config.ts`、`src/server/main.ts` |
| 画面 | `src/client/components/tasks/*`、`AccountLogin.tsx`、`AccountBar.tsx`、`SettingsView.tsx`、`App.tsx` |
| 統合試用・統合テスト | `scripts/integrated-stack.mjs`、`playwright.cross.config.ts`、`tests/cross/` |

## 3. 権限の境界

- 共通ログインの資格（実効 Group 会員＋本人紐付け）は **入口の資格だけ**。メール・LINE の内容は従来どおり受信箱／
  LINE アカウントごとの許可（read / edit / reply）で判定し、一覧・検索・件数・ページ分割・詳細・履歴・変更のすべてに先に適用する。
  権限管理者（アプリ管理者）や Group 管理者という理由では内容を読めない。
- タスクは Task サービスの委員会（viewer / editor / admin）と有効な所属で判定する。担当者は選んだ委員会の有効なメンバーだけ。
- **受信案件からの作成** は「元案件を今読める」ことを先に確認し（読めなければ存在しない場合と同じ 404。Task サービスは呼ばない）、
  タスク作成の可否は Task サービスが判定する。案件の対応状況・担当は変更しない（変更する場合は別途その編集権限が必要）。
- **元案件の表示（provenance）** は表示のたびに、閲覧者の現在の元ソース ACL で評価する。タスクだけ読める人には、元案件の存在・ID・
  リンク・件名・本文・添付のいずれも返さない（空の一覧で、関連付けのないタスクと区別できない）。権限を剥奪すると作成者本人にも表示されない。
  タスクの項目自体は Task 側の権限どおり読める。
- ブラウザが送る利用者・ソース・管理者のヘッダー（`X-Mail-User`、`X-Svc-Actor`、`X-Demo-User` など）は使わない。

## 4. 受信案件からの作成：重複防止と回復

1. 画面はフォームを開いて送信するたびに `clientOperationId`（UUID）を作り、再試行では同じ値を使う。
2. 共通 Web は「本人＋clientOperationId」をキー、本人・元案件・委員会・入力内容の指紋を値として操作記録（pending）を
   **Task 呼び出しの前に** 保存する。Task への操作 ID はキーから決定的に導く（`cg-…`）。
3. Task サービスは同じ利用者・操作 ID・内容なら再実行せず同じタスクを返す（`replayed`）。
4. 結果ごとの扱い:

| 結果 | 共通 Web の応答 | 状態 |
| --- | --- | --- |
| 作成成功 | 201（再送は 200, `replayed`） | 関連付けを保存、操作記録は complete |
| Task が拒否（権限・担当・入力） | 4xx（Task の文言） | 何も作られていない。pending を削除し、修正して再送できる |
| 応答なし・タイムアウト・5xx | 503 `task_service_unavailable` | 作成されたか不明。pending を残す。同じ内容の再試行で重複なく確定 |
| 作成後に関連付けの保存失敗 | 503 `link_pending` | タスクはある。再試行で同じタスクに関連付ける |
| 同じ ID で内容が違う | 409（他の結果は返さない） | 新しい作成としてやり直す |

二つのサービスをまたぐ原子性はない。上記は「作成済みかもしれない」状態を明示し、同じ操作の再試行で収束させる設計である。
本人の未確定の依頼は受信案件の画面に表示され、「再試行」で確定できる（本人以外には表示しない）。権限を失った後の再試行は
元案件の確認で拒否され、すでに作成されたタスクは関連付けのない通常の委員会タスクとして残る（元案件は誰にも漏れない）。

## 5. アカウント認証

採用した方式: 登録済みメールアドレスを入力 → 本人紐付け済みの Discord ID へ Bot が **確認済みメールアドレスと短時間・一回限りのコード** を DM →
同じブラウザでコードを確認 → 本人が恒久パスワードを設定 → 以後はメールアドレスとパスワードでログイン。恒久パスワードを Bot・DM・ログで扱わない。

| 項目 | 実装 |
| --- | --- |
| 資格 | 有効な本人紐付け（承認済みの根拠・メール検証済み）、有効な principal、設定した Group の **実効** 会員（直接・入れ子・設定した組織の全利用者）。未確定・期限切れ・照会拒否・不一致は拒否 |
| コード | 8 桁、5 分、1 回限り（同期的に消費）、挑戦ごと 5 回まで、再送で旧コード無効、用途（`password_setup`）と audience（公開オリジン）に結び付けたハッシュだけを保存 |
| 配送 | 本人紐付けの Discord ID だけへ。配送の受領確認がなければコードは使えない |
| 設定許可 | コード確認後 10 分・1 回限りのトークン（HttpOnly Cookie） |
| パスワード | Node 組込み scrypt。本番プロファイルは OWASP Password Storage Cheat Sheet の scrypt 最低値 **N=2^17, r=8, p=1**（32 バイト, ソルト 16 バイト）。1 回の計算に 128×N×r = 128 MiB を使うため maxmem は 144 MiB、同時計算は既定 1（最大 2）・待ちは 8 まで（超過は「現在受け付けられません」）。この構成でパスワード計算に使うメモリは最大でも約 128 MiB。定時間比較。12〜128 文字（NFC 後のコードポイント）、UTF-8 512 バイトまで、制御文字とメールアドレスを含むものは拒否。超過は切り詰めず拒否 |
| ハッシュの版 | 保存済みハッシュは本番プロファイルと完全に一致するものだけを評価する。より低いコスト（例: N=2^15 や試験用 N=2^14）の記録は評価せず、正しいパスワードでも同じ失敗応答（監査理由 `credential_profile_rejected`）になり、本人が DM コードで再設定する。低コストの試験用プロファイルはテストコードが専用の確認定数を渡したときだけ使え、設定・環境変数・production／模擬構成からは選べない |
| 制限 | 申請・確認・ログインごとのクライアント上限、全体上限、宛先ごとの DM 間隔と上限（1 分 1 通・15 分 3 通）、アカウント単位の失敗上限（15 分 5 回）。アカウントの失敗回数と宛先ごとの DM 間隔・上限はログイン状態ファイルに保存し、再起動後も有効（期限切れは保存時に削除、1 キー最大 64 件・キー総数は `maxRateKeys` 以内）。クライアント単位と全体の要求上限はメモリのみで、再起動で数え直す。コードごとの試行回数（5 回）は従来どおり保存。キー総数が上限に達し、そのアカウントの失敗を記録できないときは、パスワードを評価せず「受付不可」で断る（アカウントの存否を調べる前に判定。コード確認側は同じ状況で確認待ちを無効にする）。期限切れのキーが消えれば自動的に回復する |
| 列挙対策 | 申請は常に同じ応答。ログイン失敗は未登録・未設定・誤り・資格喪失で同じ応答。未登録でも KDF を 1 回実行 |
| セッション | 不透明トークン（ハッシュのみ保存）、無操作 30 分・最長 8 時間、毎要求で紐付け・principal・会員資格・資格情報の版を再確認。ログアウト・資格喪失・紐付け置換・パスワード再設定で失効 |
| 復旧 | 同じ確認済み紐付けへの DM コードでのみ再設定。再設定で既存の全セッション・未使用コード・他の設定許可を失効。役割やメール閲覧権限は変わらない |
| Cookie・CSRF | `__Host-` 接頭辞・Secure・HttpOnly・SameSite=Strict・Path=/。書込はすべて公開オリジンの `Origin` とカスタムヘッダー `X-SMM-CSRF: 1` が必須。CORS は提供しない。URL のクエリでコード等を受けない |
| 永続化 | `SMM_AUTH_STORE_FILE`: 資格情報・セッション・挑戦・設定許可・保存対象のカウンターを 1 文書として置換保存（`src/server/durable-file.ts`: 一意な名前の一時ファイルを排他作成・所有者のみの権限 600 で作成 → 書込 → fsync → rename → POSIX では親ディレクトリも fsync。Windows では Node からディレクトリを fsync できないため、rename は原子的だが電源断直後の rename の永続性は保証しない）。失敗時は自分が作った一時ファイルだけを消し、元のファイルを残して操作を失敗させる。ペッパー鍵による HMAC で改ざん・破損を検出し、検出時は起動を拒否（空や見本へ戻さない）。タスク関連付けファイルも同じ方式。`SMM_AUTH_AUDIT_FILE`: 仮名化した監査イベントを JSON Lines で追記（5 MiB で 1 世代ローテーション） |

**運用者による救済**（紐付けの確認後に本人以外がパスワードを解除する等）は、無認証の迂回を作らないため実装していない。
確認済みの手順（例: 本人紐付けの再確認 → 紐付けの版を上げる → 本人が再度 DM コードで設定）を運用者が決めるまで保留する。

| --- | --- | --- |
| `demo`（既定） | 従来のペルソナ切替デモ | ループバックのみ。Task ゲートウェイは任意（合成の本人対応表） |

## 6. 接続契約（非秘密）

### 6.1 svc-auth/v1（サービス間署名）

ヘッダー `X-Svc-Client`、`X-Svc-Timestamp`（ミリ秒）、`X-Svc-Nonce`（22〜64 文字の base64url）、`X-Svc-Actor`（ゲートウェイのみ）、
`X-Svc-Signature`（HMAC-SHA256 の 16 進）。正規文字列は `svc-auth/v1`・クライアント ID・メソッド・クエリ込みのパス・時刻・ノンス・
actor・本文の SHA-256（16 進）を改行で連結したもの。時刻のずれは ±30 秒、ノンスは再利用不可。クライアント ID と鍵:
`web-gateway`（共通 Web → Task）、`discord-bridge`（Discord 連携 Bot → Task）、`smm-auth`（共通 Web → 本人 bridge）。鍵はそれぞれ別の 32 バイト以上の乱数。

### 6.2 Task サービス保護 API

[タスクサービスの API](task-service/integration-api.md) を正とする。共通 Web は `/api/integration/v1` の me・一覧・作成（操作 ID 必須）・
取得・更新（`expectedVersion` 必須）・再開・履歴・メンバーを使う。

### 6.3 本人 bridge（運用者提供・未接続）

共通 Web から署名付き POST（JSON）。応答は厳密に検証し、想定外は拒否として扱う。応答には署名がないため、真正性は通信路で担保する:
`SMM_IDENTITY_BRIDGE_URL` は `https://`（証明書を検証）か、同じホストのループバック `http://127.0.0.1` / `http://[::1]` だけを受け付ける。
私設 IP を含む他ホストへの平文 http は起動時に拒否する（DM コードを含む封筒と会員判定が平文で流れるため）。Task サービスへの接続（`SMM_TASK_SERVICE_URL`）も同じ規則。

| パス | 要求 | 応答 |
| --- | --- | --- |
| `/v1/links/by-verified-email` | `{ email }`（正規化済み・完全一致） | `{ link: IdentityLink \| null }` |
| `/v1/links/get` | `{ linkId }` | `{ link: IdentityLink \| null }` |
| `/v1/principals/get` | `{ principalId }` | `{ principal: { principalId, active } \| null }` |
| `/v1/membership/effective` | `{ groupId, memberKey }` | `effective_membership/v1` の観測（`src/server/login/types.ts`） |
| `/v1/dm/login-code` | `LoginCodeEnvelope`（テンプレート `password_setup_code_v1`、確認済みメール、コード、期限、宛先の Discord ID と紐付けの版） | `{ deliveryId, status: 'delivered' }` または失敗理由。**DM を実際に送ってから** delivered を返す。同じ deliveryId で 2 回送らない |

`IdentityLink` は `linkId, version, status, email, emailVerified, discordUserId, memberKey, principalId, evidence`。
principal は共通 Web の利用者 ID と一致させる。bridge は封筒（コードを含む）を保存・記録しない。

### 6.4 Discord 連携 Bot（運用者提供・未接続）

既存 Bot が Discord で検証した interaction の `guildId`・`channelId`・操作者の `userId`（いずれも数値 ID、表示名ではない）と、
明示コマンド（list / show / create / assign / status / deadline / require / reopen）を署名付きで Task サービスへ送る。
interaction ID は操作 ID として再配信を判定し、guild/channel も指紋に含むため別チャンネルからの再送は拒否される。
既存タスクを変える assign / status / deadline / require / reopen は、Web の `expectedVersion` と同じく表示中の `version` が必須
（省略・不正は 400 VALIDATION、古ければ 409 VERSION_CONFLICT）。
返信文は応答の `reply` を使う。詳細は [タスクサービスの API](task-service/integration-api.md)。

### 6.5 direct 構成（`SMM_IDENTITY_PROVIDER=direct`、明示 opt-in・実接続は未検証）

本人 bridge の代わりに、共通 Web のプロセス内で次の 4 つの提供元を組み立てる（`src/server/runtime.ts`）。`SMM_IDENTITY_BRIDGE_URL` は不要で、
新しい内部 bridge サーバーを用意する必要もない。

**実運用・実接続の阻害要因（アプリ側の未実装。利用者に作業を求めるものではない）**

1. Directory の資格情報のライフサイクルがない。アプリは OAuth 認可・トークン発行・更新を行わず、`SMM_DIRECTORY_TOKEN_FILE` を更新し続ける既存の仕組みがあるかどうかは **未検証**（あるとは仮定しない）。
   アクセストークンには期限があるため、更新されなければ期限切れの時点で全員が拒否される。
2. 本人紐付けレジストリを既存の検証済みの権威から取り込む仕組みがない。既存の正規の権威（名簿・既存 Bot の紐付けなど）があるか、どの契約かは **未検証**（ないとも仮定しない）。
   レジストリは手作業で作るものではない（`evidence` は自己申告にすぎず、手で作った対応は権威にならない）。契約を安全に確認したうえで、その権威からレジストリを導出・準備するのは開発側の作業。
3. 実際の Bot DM 送信、配送 ID の重複排除、受領確認（ACK）がない。既存 Bot の契約は未確認。DM 未提供のまま新しく導入した環境では、**誰も最初のログインができない**（下記）。
4. Windows では起動しない（トークンとレジストリの所有者限定の権限を強制できないため）。POSIX 環境が必要。

OAuth・トークン更新・実 DM の実装は今回の対象外。上記が解消し、実接続で確認されるまで、direct 構成は合成データでの検証だけで、本番利用の準備ができたとは言えない。

| 提供元 | 実装 | 内容 |
| --- | --- | --- |
| 紐付け（links） | `src/server/account/identity-registry.ts` | Git 外の所有者限定ファイルの本人紐付けレジストリ（`SMM_IDENTITY_REGISTRY_FILE`、形式は [`deploy/identity-registry.example.json`](../deploy/identity-registry.example.json)）。照会のたびに読み直し、壊れ・権限・シンボリックリンク・読めない場合は拒否（古い内容を使わない） |
| 本人（principals） | `direct-providers.ts` + `google-directory.ts` | レジストリの有効な紐付けと、Directory の `users/{安定 ID}` で安定 ID・主メール・顧客 ID・停止/アーカイブ/削除を毎回確認 |
| 実効会員（membership） | `google-directory.ts` | 対象 Group（安定 ID）の会員一覧を全ページ・入れ子 Group まで読み、CUSTOMER（組織全体）は確認済みの顧客 ID と比較。深さ・Group 数・ページ数・会員数・応答サイズ・時間に上限。全体を読み切ったときだけ `complete` |
| DM（deliver） | `SMM_AUTH_DM_TRANSPORT` | `unavailable`（常に送信拒否）か、既存の署名付き契約 `identity-bridge`（6.3 の `/v1/dm/login-code` だけを使う） |

- レジストリ: `kind: "smm-identity-registry"`、`version: 1`、各紐付けは `linkId`・`linkVersion`・`status`（active / revoked）・`evidence`・
  `google.userId`（数値の安定 ID）と `google.primaryEmail`（正規化済み）・`discord.userId`（確認済み、`verified: true`）・`principalId`・`taskUserId`（または null）。
  未知の項目、重複（リンク・本人・Google ID・メール・Discord ID・Task 利用者。失効済みも含む）は全体を拒否。有効な紐付けは既存の利用者を指し、
  Task 本人対応表（`SMM_TASK_BRIDGE_FILE`）と同じ Task 利用者でなければならない（利用者・委員会は作らない）。紐付けを変えたら `linkVersion` を上げる（セッションとパスワードが無効になる）。
  主メールと Discord ID を含むため、所有者だけが読める権限（0600 か 0400）でなければ拒否する（他者に読めるだけでも拒否）。
- 互換性の確認範囲: 確認するのは、有効な紐付けの本人→Task 利用者が Task 本人対応表と一致することだけ。レジストリの Discord ID と、Task 側に実際に登録された
  Discord との対応（Discord バインド）は突き合わせていない。
- Directory への要求は固定オリジン `https://admin.googleapis.com` の固定 GET パスだけ。リダイレクト・401/403/404/429/5xx・タイムアウト・上限超過・
  形式外の応答はすべて拒否（非会員とはみなさない）。トークンと応答本文は記録しない。
- アクセストークン: `SMM_DIRECTORY_TOKEN_FILE` はトークンのファイルへの参照（所有者だけが読める 0600 か 0400 の通常ファイル、シンボリックリンク不可）。
  アプリは OAuth 認可・トークン発行・更新・スコープやロールの追加を行わない（阻害要因 1）。
- 変更の反映: 認可に使う情報は要求ごとに取り直す。レジストリは毎回読み直し、Directory はユーザー（本人確認と会員確認で各 1 回）と Group 全体を毎回読む。
  要求をまたぐキャッシュも、別の要求が始めた読み取りへの相乗りもない。Group からの削除・停止・アーカイブ・削除・主メールの変更は、次の要求で拒否される。
  再利用時間の設定 `SMM_DIRECTORY_CACHE_MS` は廃止した（値にかかわらず、指定すると起動しない）。
- 時間と費用: 1 回の会員確認は、ユーザー読み取りと Group 全体の読み取りを合わせて既定 4 秒（上限 4.5 秒）の 1 つの締め切りで行い、ログイン中核の提供元タイムアウト（5 秒）に収める。
  個々の HTTP 要求は 2 秒まで。認証済みの要求 1 回あたりの Directory 要求は、ユーザー 2 回・Group 1 回・入れ子を含む各 Group の会員一覧 1 ページ以上。
  入れ子が深い・会員が多いほど遅延と API 割り当て（quota）の消費が増え、429 や遅いページが 1 つでもあればその要求は拒否され、セッションは失効する（安全側）。
  実際の遅延と割り当ては未計測。ほかに、要求 1 回あたり次の費用がかかる（いずれも鮮度のためで、要求をまたいだ共有はしない）:
  - レジストリ: 紐付けの照会と本人確認（live 読み取りの前と後）で、要求 1 回につき最大 3 回、同期的に読み直し・ハッシュ計算・互換性の確認をする（ファイル上限 4 MiB）。
    その間はイベントループが止まるため、レジストリが大きいほど全要求の遅延が増える。
  - トークン: Directory への HTTP 要求のたびに（会員一覧の各ページを含む）トークンのファイルを読み直す。
  - 締め切り: 本人確認（ユーザー読み取り）と会員確認（ユーザー + Group 全体）は順番に実行され、それぞれ別の締め切り（既定 4 秒、上限 4.5 秒、
    ログイン中核の提供元タイムアウト 5 秒の内側）を持つ。このため認証済みの要求 1 回の判定には、最悪で既定値なら約 8 秒、上限値なら約 9 秒かかりうる（ファイル読み取りの時間は別）。
- 実行環境: direct 構成は POSIX のみ。トークンとレジストリは毎回、処理ユーザーの所有でグループ・他者の権限がないことを確認する。Windows では所有者と権限を
  強制できないため起動を拒否する（阻害要因 4）。Windows 上の自動テストは、テスト専用の合成ビュー（所有者と 0600 を報告するだけで、実際の Windows の権限は確認しない）で
  構成を動かしているだけで、Windows での権限の強制を示すものではない。
- DM 未提供（`unavailable`）でできること: 既存のパスワード資格（同じ `linkId`・`linkVersion` で設定済みのもの）での通常ログインと、要求ごとの再確認。
  できないこと: 初回のパスワード設定、再設定、コードだけのログイン（コードは発行されても配送されず、すぐ破棄される）。
  **新しく導入した環境で DM が未提供なら、最初のログインの手段はない**（パスワード資格がまだないため、誰もログインできない）。
- `identity-bridge` の DM 経路は、既存の署名付き DM 契約（6.3）の相手がすでにある場合だけの選択肢。その相手があるかは未確認で、direct 構成のために新たに作るものではない。
- 実応答についての前提（いずれも実接続では未確認。今回、実 API への要求は一度もしていない）:
  - ユーザー応答に `id`・`primaryEmail`・`customerId`・`suspended`・`archived` が必ずあること（欠けると拒否）。`deletionTime` があれば削除済みとして拒否。
  - 会員応答の各項目に `id`・`type`・`role` があり、USER には `status` があること（`ACTIVE` 以外や欠落は会員とみなさない）。
  - 会員の `type` が USER・GROUP・CUSTOMER のどれかであること。それ以外（外部の会員や未知の種類など）が入れ子のどこかに 1 件でもあれば、
    その読み取り全体が不完全になり、直接の会員を含めて全員拒否される（肯定的な枝があっても通さない）。
  - CUSTOMER 項目は顧客 ID だけでメールを持たないこと（メールつきの CUSTOMER が 1 件でもあれば、その読み取り全体が不完全として全員拒否）。
  - 外部や他組織の Group が入れ子にあっても読めること（403/404 が 1 件でもあれば全員拒否）。
  - 権限: 対象 Group 自体のレコード（groups.get）を毎回読むため、Group の読み取り専用権限（`admin.directory.group.readonly`）が必要。
    会員だけの読み取り専用権限（`admin.directory.group.member.readonly`）だけでは Group のレコードを読めない見込みで、その場合は全員拒否になる（安全側だが利用できない）。
    加えて、ユーザーの読み取り権限（`admin.directory.user.readonly`）と、それらを許す Admin API のロールが必要。どれもアプリは作成・付与しない。
  - 実際の遅延・API 割り当て。
