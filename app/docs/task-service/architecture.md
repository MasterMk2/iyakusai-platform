# 設計

ローカル試験版として実装した構成を示す。「本番前に決めること」は [要件](requirements.md) を参照。

## 技術

| 層 | 採用 | 理由 |
| --- | --- | --- |
| 言語 | TypeScript（Node.js 22） | 画面とサーバーで型を共有できる。 |
| サーバー | Fastify 5、入力検証は zod 4 | 小さく、テスト用の inject で API を直接検証できる。 |
| 画面 | React 19 + Vite 8 | 少人数で保守しやすい。ビルド後はサーバーが静的配信する。 |
| 保存 | ローカル JSON ファイル | 外部サービスなしで再起動後も保持できる。試験版専用。 |
| テスト | Vitest 5（単体・API）、Playwright 1.64（Chromium） | 実ブラウザで主要な操作を確認する。 |

すべて無料のオープンソースで、外部 API や有料サービスは使わない。

## 構成

```text
Web UI（src/client） ──HTTP──> API（src/server/http/app.ts） ─┐
                                                              ├─> TaskService（src/server/domain）─> Store（src/server/storage）
模擬 Bot コンソール ──HTTP──> MockBotAdapter（src/server/bot） ┘        │
                                                                 権限確認・履歴・版・操作 ID
```

- `src/shared/`：型、入力の検証規則、日付、表示ラベル。画面とサーバーで共有する。
- `src/server/domain/`：`TaskService` が委員会タスクの共通操作。権限確認（`permissions.ts`）、履歴、版の確認、操作 ID による重複防止をここで行う。HTTP や Bot の形式に依存しない。
- `src/server/http/`：HTTP の入出力と模擬ログイン（`X-Demo-User` ヘッダー）。入力はそのまま `TaskService` に渡し、検証と権限判定はドメイン側で行う。
- `src/server/bot/`：模擬 Bot。`/todo <操作> 名前:値` 形式のテキストを解析し、`TaskService` の操作に変換して返信テキストを作る。チャンネルと外部アカウントは、サンプルデータ内の架空の対応表（`mock-…`）だけで内部の委員会・利用者に対応付ける。実際の Discord、外部の履歴、認証情報は読まない。
- `src/server/storage/`：保存先の抽象（`Store`）、ファイル保存、テスト用のメモリ保存、デモ用の障害注入。

## データ

| データ | 主な項目 |
| --- | --- |
| 委員会 | ID、表示名、説明 |
| 利用者 | ID、表示名、架空のメール、模擬ログイン用の説明 |
| 所属 | 委員会 ID、利用者 ID、役割（viewer / editor / admin）、有効状態 |
| タスク | ID、委員会 ID、タイトル、説明、担当者 ID、期限（日付のみ）、状態、要件 4 項目、版、作成・更新の日時と人物 |
| 変更履歴 | タスク ID、版、種類（作成・変更・再開）、変更者、日時、入口（Web・模擬 Bot）、操作 ID、項目ごとの変更前後 |
| 役割の変更記録 | 委員会、対象者、変更者、日時、変更内容 |
| 操作記録 | 入口・人物・操作 ID、内容の指紋、結果の参照。再送の判定に使う |
| 模擬 Bot の対応表 | 模擬チャンネル → 委員会、模擬アカウント → 利用者 |

## 権限

- すべての読み取りと変更で、操作する人物の **有効な所属と役割** を `TaskService` 内で確認する。画面の表示制御だけには頼らない。
- 委員会単位の要求（一覧・作成・メンバー）で所属がなければ 403。
- タスク ID を直接指定した要求で、タスクがない・所属外・所属が無効のいずれも 404（存在を明かさない）。所属していて役割が足りない場合は 403。
- 模擬 Bot はチャンネルに対応する委員会のタスクだけを扱う（他委員会のタスクは 404 と同じ扱い）。
- 再送で過去の結果を返す場合も、現在の権限で確認してから現在の内容を返す。

## 変更履歴・同時編集・再送

変更は次の順で 1 件ずつ（プロセス内で直列に）処理する。

1. 操作 ID があれば、同じ入口・人物・ID の記録を探す。あれば内容の指紋を比べ、同じなら再実行せずに現在の内容を返す（`replayed: true`）。違えば `IDEMPOTENCY_CONFLICT`。模擬 Bot ではチャンネルの委員会も指紋に含めるため、別チャンネルでの同じ ID の再送は拒否され、他チャンネルのタスクは返らない。再送の応答も現在の権限とチャンネルの範囲で確認する。
2. 現在の状態の **複製** に変更を適用する。権限、入力、担当候補、状態遷移、版（`expectedVersion`）を確認し、変更点がなければ `NO_CHANGE`。
3. タスク・履歴・操作記録を含む状態全体を 1 回で保存する（一時ファイルを排他作成して書込・fsync → rename → POSIX ではディレクトリも fsync）。
4. 保存が確定したときだけ、メモリ上の状態を置き換える。rename 前の失敗ではメモリもファイルも変更前のまま残り、`SAVE_FAILED` を返す。操作記録も残らないため、同じ操作 ID で再試行できる。rename 後の確定（ディレクトリの fsync）を確認できなかった場合と、保存ファイルが他から変わっていた場合は、メモリ上の状態を使わずに次の操作の前に読み直す（詳細は [統合 API](integration-api.md)「単一プロセスと保存」）。

Web API の変更要求は `expectedVersion` が必須。模擬 Bot は Discord の操作のように版を持たないため省略でき、`version:N` を付けた場合だけ版を確認する。

## 安全のための制限

- サーバーは 127.0.0.1 / localhost / ::1 にだけ待ち受け、Host ヘッダーもループバックだけを受け付ける（DNS リバインディング対策）。
- 変更要求は JSON のみ受け付け（text/plain は 415）、別サイトの Origin からの変更は拒否する。
- Content-Security-Policy（`default-src 'self'`）、`X-Frame-Options: DENY`、`nosniff`、API 応答の `no-store` を付ける。
- 画面はブラウザに Cookie や localStorage を保存しない。
- 画面に出す保存先の説明や起動時の表示には、作業フォルダからの相対パスだけを出す。

## 保存の境界

- 既定の保存先は作業フォルダの `data/demo-state.json`（Git 対象外）。E2E は `data/e2e/`、テストは `data/test-runs/` を使い、終了後に削除する。
- 1 プロセスが状態全体を 1 文書として読み書きする。複数プロセスでの同時利用、複数台、バックアップ、利用者ごとの認証は対象外で、本番の共有保存ではない。
- 電源断に対する保存の永続性（ファイルとディレクトリの fsync）は POSIX だけ。Windows ではディレクトリを fsync できないため保証しない。

## デモ専用の機能

- 模擬ログイン（人物切り替え）と、その注意書き。
- 障害注入（`/api/demo/faults`）：指定回数の読み込み失敗・保存失敗と応答遅延。
- サンプルデータの初期化（`/api/demo/reset`）。

これらは試験のための機能で、本番では削除するか、管理者だけに制限する前提。

## 保護モード（共通 Web・Discord 連携）

`DTM_MODE=protected` は `src/server/integration/` の内部 API（`app.ts`）だけを公開する。要求は svc-auth/v1 で署名され（`signing.ts`）、
送信元ソケットも許可リストで確認する（`config.ts`）。ゲートウェイは署名済みの操作者ヘッダーで、Discord 連携は対応表（guild/channel → 委員会、
Discord 利用者 → 内部利用者）で、どちらも同じ `TaskService` を呼ぶ（`discordBridge.ts`）。Discord の操作は `scopeKey`（guild/channel）を
操作記録の指紋に含め、別チャンネルからの同じ interaction の再送を拒否する。仕様は [統合 API と Discord 連携契約](integration-api.md)。
