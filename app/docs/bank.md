# 銀行の連携（GMOあおぞらネット銀行 API）

委員会の銀行口座を、基盤が API で読めるようにするための土台です（2026-11-06 から）。この版でできるのは、**接続のための秘密の値を安全に保管すること**と、**口座が読めるかを確かめること**までです。入出金明細を入金確認（[payments.md](payments.md)）に自動で取り込む処理は、次の版で作ります。

いまは銀行の試験用の環境 **sunabar**（架空のお金）だけにつながります。本番の銀行は、sunabar で確かめてから別に有効にします。

実装は次の 3 か所です。

- `app/src/server/bank/`：設定（`config.ts`）、トークンの保管（`vault.ts`）、銀行への要求（`client.ts`）、接続の流れ（`service.ts`）、API（`routes.ts`）
- `app/src/shared/bank.ts`：画面と共有する型
- `app/src/client/components/bank/`：設定のパネルと、銀行から戻る画面

## 1. できること

| 操作 | 中身 | 使える人 |
|---|---|---|
| 状態を見る | 設定 →「銀行の連携」。未接続・接続済み・期限切れ・要再接続、許可の範囲、接続した人と日時、トークンの期限、最後の更新、最後のエラー | 権限管理者、会計を見る |
| 銀行と接続する | 押すと銀行の画面に移る。銀行のログイン ID とパスワードで入って「許可する」を押すと、基盤に戻って接続が終わる | 権限管理者 |
| 接続を確かめる | 銀行の口座一覧と残高を読む。口座番号は下 4 桁だけを出す | 会計を見る |
| 接続を切る | 基盤に保存したトークンを消す。銀行側の許可は期限まで残る（銀行に取り消しの API がない） | 権限管理者 |

臨時スタッフ、権限のない委員、ログインしていない人には、パネルも API も出しません（403・401）。Bot のデータソースや内部の経路にも銀行の API は足していません。

## 2. 使い方

1. 運用者が `bank.json` などを置く（[deployment.md](../../docs/deployment.md) §4「銀行の連携」）。
2. 権限管理者が 設定 →「銀行の連携」→「銀行と接続する」。
3. 銀行の画面でログインし「許可する」。基盤の「銀行との接続を仕上げています…」の画面を経て、設定に戻り「銀行と接続しました」と出る。
4. 会計を見る人が「接続を確かめる」で、口座と残高が読めるかを確かめる。

銀行の許可（認可コード）は **60 秒** で使えなくなります。銀行の画面で長く止まったときは、もう一度「銀行と接続する」から始めます。

## 3. 安全のための作り

**秘密の値の置き場所**

- クライアントシークレットとトークン用の鍵は、設定のフォルダのファイル（所有者だけが読める 600）に置く。中身をログ・画面・エラーの文に出さない。
- 銀行のトークン（アクセストークン・リフレッシュトークン）は、人が見たり写したりしない。接続の流れでサーバーが受け取り、そのまま保管する。
- トークンはデータのフォルダの `bank-tokens.json` に **AES-256-GCM で暗号化**して書く。
  - 鍵は、トークン用の鍵から HKDF-SHA256 で用途を分けて作る。
  - 追加データに環境と client_id を入れる。別の環境・別のクライアント・別の鍵のファイルは開けず、使わない（画面に「要再接続」と出る）。
  - データのフォルダの写しだけでは中身を読めない。
- バックアップ（`ops/backup.ts`）には入れない。復元したら、設定の画面からつなぎ直す。

**送り先と権限を広げない**

- 銀行の URL はコードで固定する。設定のファイルでは変えられないので、ファイルを書き換えてもシークレットやトークンをほかへ送れない。
- 銀行への要求は、HTTP のリダイレクトを追わない。
- 許可の範囲は `private:account` と `private:virtual-account` だけに絞る。次の 3 か所で確かめる。
  - 設定（振込のスコープがあれば起動時に断る）
  - 銀行への認可の要求（この 2 つだけを求める）
  - 銀行の答え（ほかの権限が付いていたら保存せずに止める）
- 基盤から銀行へ送れるのは、トークンの要求と照会 2 つ（口座一覧・残高）だけ。どの API にも送れる関数は作っていない。振込の関数もない。

**接続の流れ**

- 権限管理者が「接続する」を押すと、サーバーが一回限りの `state` を作る（本人に結び付け、10 分で失効）。
- 銀行はブラウザを `/bank/callback` に戻す。
  - API の経路にしていないのは、別のサイトから戻る遷移では基盤の Cookie（SameSite=Strict）が送られず、API の入口でも断られるため。
  - この画面は、URL の `code`・`state` をすぐに履歴から消す。ほかを読み込む前に、同じサイトの要求として `/api/bank/oauth/complete` に送る（CSRF のヘッダー付き）。
  - `/bank/callback` は `Cache-Control: no-store`・`Referrer-Policy: no-referrer` にする。
- `state` は、結果にかかわらず 1 回で使い切る。別の人が送ったときも断る。銀行の画面で許可しなかったとき（`error=access_denied`）も、使い切って記録だけを残す。

**更新と失敗**

- アクセストークンは、期限の半分を過ぎたら（または残り 1 分）、使う前にリフレッシュトークンで更新する。
- 更新は同時に 1 回だけ走らせる。新しいトークンを保存してから使うので、銀行がリフレッシュトークンを差し替えても失わない。
- 銀行が更新を断ったとき（`invalid_grant`）は、トークンを消して「要再接続」にする。通信の失敗なら、トークンを残して最後のエラーに出す。
- リフレッシュトークンが返らないときは、期限まで使い、そのあとは「期限切れ」としてつなぎ直してもらう。

**記録**

`SMM_MAIL_DIR/bank-audit.jsonl` に、日時・操作・した人・結果を 1 行ずつ足す。トークン・認可コード・銀行の答えは書かない。最後のエラーの文は `bank-state.json`（秘密を含まない）に置く。

## 4. 権限

サーバーで毎回確かめます。

| 権限 | できること |
|---|---|
| 権限管理者 | 状態を見る、接続する、接続を切る。Redirect_uri の登録値を見る |
| 会計を見る（`accounting.view`） | 状態を見る、接続を確かめる |
| それ以外の委員・臨時スタッフ | なし（403） |

権限管理者であることだけでは「接続を確かめる」（口座と残高）は使えません。入金確認と同じく、設定 →「会計の権限」で「会計を見る」を付けます。

## 5. データの置き場所

| ファイル | 中身 |
|---|---|
| `config/bank.json` | 銀行の連携の設定（下の例） |
| `config/bank-client-secret` | クライアントシークレット（1 行、600） |
| `config/bank-token.key` | トークンを暗号化する鍵（32 バイト以上の乱数、600） |
| `SMM_MAIL_DIR/bank-tokens.json` | 暗号化したトークン（600。バックアップに入れない） |
| `SMM_MAIL_DIR/bank-state.json` | 要再接続かどうかと最後のエラー（秘密を含まない） |
| `SMM_MAIL_DIR/bank-audit.jsonl` | 操作の記録 |

```json
{
  "version": 1,
  "environment": "sunabar",
  "accountType": "corporation",
  "clientId": "銀行の画面に出たクライアントID",
  "clientSecretFile": "/config/bank-client-secret",
  "clientAuth": "basic",
  "redirectUri": "https://app.example.org/bank/callback",
  "scopes": ["private:account", "private:virtual-account"],
  "tokenKeyFile": "/config/bank-token.key"
}
```

- `accountType`：`corporation`（法人。既定）か `personal`（個人）。振込入金口座の API は法人の側にある。
- `clientAuth`：`basic`（ベーシック認証。既定）か `post`（クライアントシークレット認証）。銀行の画面の「認証タイプ」と同じにする。
- `redirectUri`：銀行に登録した値と 1 文字も違わないように書く。パスは `/bank/callback` だけ。https にする（http は手元の試験の localhost だけ）。
- `scopes`：省くと 2 つとも。`private:account` は必須（接続の確認に使う）。
- `bank.json` が使えないとき（知らない項目・振込のスコープ・鍵の権限など）は、銀行の連携だけを無効にして起動し、理由を起動のログに出す。

## 6. 銀行の画面での設定（sunabar）

| 項目 | 値 |
|---|---|
| 認可利用 | ON |
| サービス名 | 任意（例：IyakusaiTest） |
| 認証プロトコル | OAuth2.0 だけ |
| 認証タイプ | ベーシック認証（`bank.json` の `clientAuth` と合わせる） |
| Redirect_uri | `https://<公開ホスト>/bank/callback` |
| スコープ | `private:account` と `private:virtual-account` だけ ON |

使っている銀行の URL（コードに固定）：

- 認可：`https://api.sunabar.gmo-aozora.com/ganb/api/auth/v1/authorization`
- トークン：`https://api.sunabar.gmo-aozora.com/ganb/api/auth/v1/token`
- 照会：`https://api.sunabar.gmo-aozora.com/corporation/v1/accounts`・`/accounts/balances`

出典は、sunabar のチュートリアルが配る Postman の定義（法人）と、GMOあおぞらネット銀行の「オープン API 仕様書 認可編（OAuth2.0）」。

## 7. 試したこと

- `tests/unit/bank.test.ts`（12 件）
  - 設定の検査：振込のスコープ・本番・知らない項目・Redirect_uri の形を断る。鍵の権限を確かめる。
  - 暗号化の往復と改ざん・別の鍵・別のクライアントでの失敗。
  - 認可 URL の形（`%20`、`+` を使わない）、Basic とパラメーターの送り方、広すぎる許可を断る。
  - `state` を本人に結び付け・1 回で使い切り・失効させる。
  - 期限の半分での更新（同時に呼んでも 1 回、差し替えたリフレッシュトークンを保存）。
  - 更新を断られたら消し、通信の失敗なら残す。
  - リフレッシュトークンが無いときの期限切れ。照会の下 4 桁。
- `tests/contacts/bank-http.test.ts`（4 件）
  - 権限ごとの 401・403・可否、設定が無いときの答え。
  - 戻りの画面が別のサイトからの遷移で開け、`no-store` になること。同じ遷移で API は断られること。
  - 接続 → 確認 → 切断を通し、どの答え・どのファイルにもトークン・シークレット・口座番号の全桁が入らないこと。
  - 銀行の画面で許可しなかったときの扱い。

銀行は、どれもテストの中の偽物です。
