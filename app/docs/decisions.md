# 決定事項の台帳

委員会が決めたことを、議論の場（役員会・定例・部会・メール）とは別の 1 か所に残す台帳です（2026-11-03）。
「知らないところで決まったことが後から流れ込む」「何を変えたかを共有したい」という委員の要望に応えるためのものです。

## できること

- **一覧**：決定事項を新しく決めた順に並べる。内容・詳しい内容・出典・タスクの言葉で探す。部局・状態（有効・変更された・取り消し）・決めた日の期間で絞る。
- **詳細**：決めた内容、出典、関係するタスク、変更の流れ（この決定がどれを変えたか、どれに変えられたか。取り消した変更も残る）、履歴を見る。
- **登録**：一覧の「決定を登録」から手入力する。
- **登録の入口（3 か所）**
  - メールのスレッド：「決定として登録」。件名・受信日・出典のリンクが入った状態で開く。「やめる」で、来た画面に戻る。
  - 公式LINE の会話：「決定として登録」。会話の最後の発言の日・出典のリンクが入った状態で開く。模擬の会話（合成データ）には出さない。
  - 議事録（Bot タブの議事録）：確定した議事録の画面の「決定事項を台帳に登録」。AI が拾った決定の項目を選んで、部局と決めた場を選んで登録する。確定の前（下書き）には出さない。
- **変更**：詳細の「変更として登録」で、新しい決定が古い決定を置き換える。古い決定は「変更された」になり、新しい決定に「何を変えたか」の一言が付く。
- **取り消し**：登録した人と権限の管理者が取り消せる。取り消しは「取り消しを戻す」で元に戻せる（置き換えていた古い決定も、有効に戻る）。
- **ホーム**：「最近の決定・変更」のカード（直近 5 件）から一覧へ。
- **Bot**：統合アプリ側は、`POST /v1/bot/datasource` の `sources` に `"decisions"` を求められると、最近変わった決定を応答に含める（[契約](../../docs/contracts/bot-datasource.md) §3）。Bot は `[kiban]` の `sources` に `"decisions"` を足すと `kiban/decisions.md`（`/ask` の根拠）を作る。週1回のタスク一覧の「今週の決定・変更」は、`sources` に関係なく `decisions` だけを別の要求で取る（[bot/docs/weekly-tasks.md](../../bot/docs/weekly-tasks.md)）。

上のタブは増やしていません。決定事項はホームから入ります（開いている間はホームのタブが強調されます）。

## 使い方

1. **手入力**：一覧の「決定を登録」→ 決定の内容・決めた日・決めた場・関係する部局（一つ以上）を入れて登録。出典とタスク ID は任意。
2. **変更**：詳細の「変更として登録」→ 新しい内容を入れ、「何を変えたか（一言）」を必ず書く。決めた日は今日になり、決めた場は元のまま（違うときは直す）。
3. **取り消し**：詳細の「取り消す」→ 理由を書いて（任意）取り消す。戻すときは「取り消しを戻す」。
4. **議事録から**：確定した議事録の画面で、「決定事項を台帳に登録」の項目にチェックを入れ、部局と決めた場を選んで「選んだ項目を登録」。
   - 項目の文は AI が拾ったもののまま登録される。直すときは、登録のあとで決定の「内容を直す」を使う。
   - 文が 100 字を超えるときは、100 字までを内容にし、残りを詳しい内容に入れる（何も消えない）。
   - 同じ項目をもう一度登録しても一件のままで、既にある決定へのリンクが出る（部局や場を変えても同じ）。

## データの置き場所

- **本番**（Discord ログイン・受信箱（`SMM_MAIL_DIR`）を使う）：受信箱の保存先の `decisions.sqlite3`。メール・連絡先・議事録と同じフォルダにあり、受信箱のバックアップ（`app/src/server/ops/backup.ts`）に含まれる（`mailbox/decisions.sqlite3`、件数は `decisions.decisions`・`decisions.decision_history`）。
- **デモ**（`SMM_AUTH_MODE=demo`）：データファイル（`SMM_DATA_FILE`）と同じフォルダの `decisions.sqlite3`。空のときだけ、合成の初期データ（変更の例・取り消しの例を含む）が入る。
- 決定は削除しない。変更・取り消し・内容の直しは、履歴（`decision_history`）に直す前の内容（`before_json`）とともに残る。

## 権限

| 操作 | 誰ができるか |
|---|---|
| 読む・一覧・詳細 | 委員（ログインした委員全員）。臨時スタッフは読めない |
| 登録・内容を直す・変更として登録 | 委員全員（臨時スタッフは不可） |
| 取り消し・取り消しを戻す | 登録した人と権限の管理者 |
| 議事録から登録 | 委員全員。ただし、確定した議事録で、閲覧範囲が「委員全員」のものだけ。臨時スタッフは不可。閲覧範囲が「選んだ人だけ」の議事録からは、だれも登録できない（**委員長の確認待ち**：この扱いは、閲覧範囲の権限の判断なので委員長に確認する） |

権限はサーバー側で確かめる（画面で隠すだけにしない）。臨時スタッフは、読むことも書くこともできない（`403`）。権限の管理者は `canManageAccess` で判定する。議事録からの登録は、議事録の口で、見られる人か・確定しているか・閲覧範囲が委員全員か、をサーバーが確かめる。

## 有効にする方法

- **本番**：Discord ログインで受信箱（`SMM_MAIL_DIR`）を設定して起動すると、自動で有効になる。追加の設定はない。
- **デモ**：`SMM_AUTH_MODE=demo` で起動すると、自動で有効になる（合成データ）。
- **Bot へ出す**：統合アプリ側は上記で有効。Bot 側は `kiban` の `sources` に `"decisions"` を足すと写し（`kiban/decisions.md`）を作る。週1回の一覧の「今週の決定・変更」は、`[weekly]` と `[kiban]` の接続の設定があれば `sources` に関係なく出る。統合アプリ側だけを先に出しても、Bot の動きは変わらない（求めない応答の形は従来のまま）。
- **切り戻しの順番**：統合アプリをこの版より前へ戻すときは、先に Bot の `kiban.sources` から `"decisions"` を外して Bot を再起動する。旧版の統合アプリは知らない `sources` を 401 で断るため、外さずに戻すと物品・受信箱の写しまで更新が止まる。
- 無効のとき（受信箱もデモもない起動）は、一覧・詳細の入口を出さず、Bot の口は `decisions: null` を返す（`decisions` を求めたときだけ）。
- `decisions.sqlite3` を開けないとき（壊れている・形式の版が違う）も同じく無効になり、起動のログに「決定事項だけを止めました」と出る。メール・物品・タスク・カレンダーなどほかの機能は動く（2026-11-04 から。それまではアプリ全体が起動しなかった）。ファイルは変更しないので、退避するかバックアップから戻して再起動する。

## 規則の要点

- **変更できるのは有効な決定だけ**。変更されたものと取り消されたものは、内容を直せない（履歴の一貫性のため）。
- **版番号で同時編集を防ぐ**。古い版からの直し・変更・取り消しは `409`（「ほかの人が先に変更しました」）。画面は `409` のあと、「最新の内容を読み込む」で読み直せる（入力は消える）。
- **同じ決定を二度変更できない**。先に変更された決定への二つ目の変更は `409`。
- **取り消しを戻せるのは、置き換えた古い決定がまだ有効なとき**。古い決定がほかの変更を受けていれば、`409`（「変更元の決定が、ほかの変更を受けているため戻せません」）。
- **登録の再送は二重にならない**。画面は登録ごとに記録（トークン）を持つ。同じ記録で、同じ内容の再送は最初の決定を返す。同じ記録で、内容が違う再送は `409` で保存しない（保存された内容を一覧で確かめる。内容を変えるなら「内容を直す」か「変更として登録」）。
- **議事録の項目の記録は、サーバーが作る**。記録は「議事録の番号・項目の番号」で、画面からは送れない（`minutes-` で始まる記録は、汎用の登録では `400`）。同じ項目を登録すると、部局や場が違っても、既にある決定を示す。
  - 2026-11-06 から、議事録の下書きをコメント付きで AI に差し戻せる（確定後の訂正の間も）。AI が直した下書きは項目の番号が振り直されるので、記録には「AI が何回直したか」も入れる（`minutes-<会議>-r<回>-<番号>`。最初の下書きは今までどおり `minutes-<会議>-<番号>`）。前の下書きから登録した決定は台帳に残り、新しい下書きの同じ番号の項目は別の決定として登録できる。訂正中の画面は、その議事録から台帳に登録した件数を出し、台帳で直すよう促す。
- **議事録からの登録は、サーバーが議事録の項目の文を読んで決定を作る**（画面から文は送らない）。次のときは断る：確定していない（`409`）、閲覧範囲が「選んだ人だけ」（`403`）、会議の日が実在しない日付（`422`）、選んだ項目が議事録の下書きにない（`422`）。
- **閲覧範囲は登録のときに確かめる**。登録のあとで議事録の閲覧範囲を狭めても、登録した決定は残る（決定は委員全員が読める）。
- **入力の上限**：決定の内容 100 字（1 行）、詳しい内容 2,000 字、部局 10 個、出典 5 件、関係するタスク ID 20 件。出典のリンクは、このアプリの中の場所（`#/` で始まる）だけ使える。
- **使えない文字**：決定の内容は 1 行（改行と制御文字を入れない）。
- **一覧の期間**：`from`・`to` は実在する日（YYYY-MM-DD）だけ。`2026-02-30` などは `422`。

## 保存と Bot の口

- 部局は **タスクの部局と同じキー**（英小文字 2〜16 字）。画面では、タスクの部局の名前で出す。名前のない部局は、英字の名前のまま見せる。
- Bot へは、登録者・直した人の名前も ID も出さない。出典・履歴・タスク ID・取り消しの理由も出さない（試験で確かめている）。

## 試したこと

- **保存（単体試験 25 件）**：登録・再送（同じ内容なら最初の決定、違う内容なら保存しない）・議事録の記録（内容によらず最初の決定）・内容の直し・変更（置き換え）・連続した変更の拒否・古い版の拒否・取り消しと戻し（置き換えた古い決定の有効化・戻せない場合）・取り消した変更が連鎖に残ること・一覧の絞り込み・並び順・部局のキー・デモの初期データ。
- **API（12 件）**：権限（未ログイン・臨時スタッフ・権限の管理者）、登録と再送（同じ内容・違う内容の `409`）、議事録の記録の予約（`400`）、入力の不正（400 と 422 の使い分け）、一覧の絞り込み（実在しない日は `422`）、変更の流れと履歴、版の衝突、取り消しと戻し、取り消し機能が無いとき。
- **議事録からの登録（HTTP・Discord ログイン 2 件）**：確定の前は `409`、確定のあと、同じ項目の二度目は同じ決定、範囲外の項目は `422`、100 字を超えた分は詳しい内容へ。閲覧範囲が「選んだ人だけ」の議事録と、臨時スタッフ（台帳の読み書きも、議事録からの登録も）は `403`。Discord ログインの経路で確かめている。
- **Bot の口（4 件）**：求めないときは従来の応答の形、求めたときだけ `decisions` が入る、3 つの口を同時に求めても通る、重複や未知の口は `401`、委員の ID が含まれない。
- **バックアップ（1 件）**：`decisions.sqlite3` が受信箱の複製に入り、件数が記録される。
- **議事録の項目の文の分け方（5 件）**：題名 100 字と詳しい内容、改行の扱い、記録の形。**入口の URL（11 件）**：メールと LINE の入口の受け渡し、出典リンクの検査、日付の検査、やめるで戻る先。
- **ゲート**：`npm run lint`・`npm run typecheck`・`npm run build` は通過。全体の `vitest run` は 1,109 件中 36 件が失敗（基準表の 36 件と名前が一致し、新しい失敗は 0 件）。Bot は変えていないので、Bot の unittest は回していない。
- **E2E の spec**：決定事項の文言・セレクタ（「決定として登録」など）に当たる箇所はない。実行はしていない。
- **未確認**：今回の画面の直し（一覧の再読み込み、議事録の入口の表示条件、LINE の模擬の入口の非表示、フォームの見出し、「最新の内容を読み込む」）は、型検査と build と単体・API 試験だけで確かめた。画面の描画と操作（ブラウザでの確認）は行っていない。Playwright の E2E は実行していない（固定ポートの作業と衝突するため。spec は追加していない）。

## 残り

- **Bot 側の読み取り**：作ってある（`kiban.py` の `render_decisions`、`weekly_cog.py` の `_load_decisions`）。契約 §3 の形と、統合アプリの応答（`decisions/bot.ts`）・Bot の読み方（`decisions_logic.py`）は 2026-11-04 に照合した。本番の Bot で `sources` に足すのは運用の判断。
- **議事録の項目の文は、登録の前に直せない**：確定した議事録の AI の文のまま登録される。直すには登録のあとで「内容を直す」を使う。登録の前に直せるようにするかは、画面の作りの判断として残す。
- **閲覧範囲「選んだ人だけ」の扱い**：登録できないことは決めてある。この扱いそのものは委員長の確認待ち。
- **描画と操作の確認**：議事録の入口・公式LINE の入口（本番の会話）・一覧の再読み込みを、ブラウザで操作して確かめる。E2E の spec は統合のときに主担当がまとめて回す。
- **一覧の絞り込み**：画面の中だけ。ホームから戻ると消える（URL に持たせるのは後の作業）。
- **検索**：部分一致（`LIKE`）。件数が数千に増えたら索引や全文検索を考える。
- **変更された決定の内容は直せない**：誤字を直すには、新しい決定として変更するか、履歴から元の内容を手で戻す。
- **部局の一覧**：タスクの部局が無いとき（タスクの部局の印が付いていない Task API）は、一覧にない部局の名前を手で入れる欄を使う。
