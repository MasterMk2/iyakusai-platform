# 要件（テスト版）

## 文書の位置づけ

この文書は、合成データだけで動くローカルのテスト版（`0.1.0-test`）の要件を整理する。
区分は次のとおり。

- **必須**：利用者が今回のテスト版に求めた要件。
- **採用（テスト既定）**：テスト版のために選んだ既定値。本番での確定ではない。
- **実装済み**：このリポジトリのコードとテストで確認できる動作。
- **提案**：将来の検討案。未実装。
- **本番前の決定事項**：実メール接続や本番利用の前に決める事項。

テスト版は合成データとモックの受信コネクターだけを使う。実メールへの接続、送信、自動返信、
接続元での移動・削除・既読化は行わない。実メールに対する保護の有効性は検証していない。

## 委員会共有メールの閲覧方針（確定）

現役委員全員が部署を問わず、承認済みの委員会共有受信箱の本文・添付を閲覧する。
個人・未分類・未承認の受信箱は対象外。編集は従来の Grant に従い、送信・返信・削除の権限は広げない。
読取には要求ごとの検証済み会員根拠と、共有受信箱・配送先の厳密な一致を必要とする。
詳細と実接続の保留事項は [委員会メールの扱い](../../docs/mail.md) を参照。
この方針の承認は委員会展開の完了を意味しない。本人の最小認証公開に追加の前提は設けない。
今回の最終検証結果は確認後に追記する。従来のテスト記録だけで、この変更の全検査や UI が確認済みとは扱わない。

## 採用したテスト既定値

| 項目 | 採用した既定値 |
| --- | --- |
| 担当者 | 任意・単独。担当候補の条件は従来の受信箱 Grant に従う。共有本文・添付の全員閲覧で候補や編集権限を自動的に増やさない。 |
| 対応状況 | 未対応 / 対応中 / 保留 / 完了。すべての状態間で変更でき、完了から再開できる。 |
| 「完了」の意味 | アプリ内の対応状況だけを表す。返信を送信したことを意味しない（送信機能はない）。 |
| 対応情報の共有範囲 | 担当・状態・ラベル・メモ・履歴はすべて Receipt 単位。複数受信箱で共有する既定値は採用していない。 |
| スレッドの範囲 | 受信箱ごと。同じ会話が 2 つの受信箱に届いた場合は、受信箱ごとに別スレッドとして表示する。 |
| スレッドの判定 | References の先頭 → In-Reply-To → Message-ID の順でキーを決める。件名だけでは結合しない。 |
| 重複の判定 | Receipt は (コネクター, 接続元受信箱, 接続元メール ID)。Message は Message-ID と内容ハッシュが一致した場合だけ共有する。 |
| 宛先表示の方針 | To/Cc の画面表示を絞り、Bcc は保存も表示もしない。これは表示上の規則で、共有受信の承認や配送先を推定する根拠にはしない。承認済み共有メールの本文・添付に宛先が記載されていても、部署による省略や表示停止の条件にはしない。 |
| 配送メタデータ | 接続元キー・接続元メール ID・Delivered-To・Received 等は保存するが API で返さない。共有 Message の ID も返さない。 |
| 権限なしの応答 | 会員根拠がないメール読取は 403。検証済み会員でも、存在しない ID と対象外の ID は同じ 404 本文。編集 Grant がない利用者の更新は 403。 |
| 権限管理 | 管理・同期の既存権限は変更しない。デモ管理者は非会員 fixture でメール読取 403。管理権限から会員根拠を発行しない。 |
| デモ操作 | サンプルのリセットと障害シミュレーションは全ペルソナのデータ・要求に影響するため、デモ管理者だけが実行できる（UI は管理者以外に表示せず、API は 403）。モック同期の実行中のリセットは 409 で拒否する。 |
| 接続元の制限 | ループバックのホスト名と待ち受けポート以外の `Host` を 421 で拒否する（DNS リバインディング対策）。本番の認証・接続制御の代わりではない。 |
| 検索の対象 | 件名・差出人・本文・添付名。メモは検索しない。 |
| 添付ファイル | 合成テキスト添付だけ。`application/octet-stream` の添付ダウンロードとして返し、画面内では開かない。 |
| リンク | `href` を除去した文字列として表示し、URL は CSS で文字表示する。自動でも手動でも遷移しない。 |
| 外部リソース | 画像・CSS・フレーム等は読み込まない。画像は「画像をブロックしました」と表示する。画像を許可する操作はない。 |
| ページサイズ | 一覧は 1 ページ 5 スレッド（API は最大 50）。 |
| 保存 | `data/demo-state.json`（Git 管理外）に単一プロセスで保存する。本番の複数利用者向け保存ではない。 |
| 監査 | 受信ごとの変更履歴（操作者・時刻・項目・前後値）と、権限変更・同期の監査ログ。メモ本文は履歴に入れない。 |

| 区分 | 内容 |

| 確定した利用者指示 | 現役委員全員が、部署を問わず委員会共有受信箱すべての本文・添付を閲覧する。個人メールは対象外。送信・返信・削除の権限は広げない。 |
| 採用する実装方針 | 要求内の検証済み会員根拠、現在の有効状態、`committee-shared` の明示スコープ、運用者が承認した完全一致の対象リスト、Receipt の配送先結合を検査する。詳細は [閲覧方針](../../docs/mail.md)。 |
| 保留（実接続の根拠） | ヘッダー由来のアドレス候補は権限分類が未完了。Delivered-To / Original-To の証跡はなく、記載された GAS 実行アカウントの現在の本人性も未検証。実アドレスの許可リストは作らず、実メールは有効化しない。 |
| 保留（接続と展開） | 実取得経路、認証情報、永続アクセス、実データ取り込みは未設定・未実施。本人の初回登録・ログイン確認後に委員会全体へ展開する段階であり、展開済みと扱わない。 |

### メールボックスの 4 種類

| 種類 | 内容 | 取得と閲覧の扱い |
| --- | --- | --- |
| 個人の受信箱 | 1 人の個人メールボックス。 | 所有者が読めても対象外。取得・取り込み・検索・表示を拒否する。 |
| 委員会の共有・委任受信箱 | 委員会共有として分類し、運用者が正確な取得元を承認した受信箱。 | 1 つの正規取得元を 1 回だけ取得する。検証済みの現役委員全員に本文・添付の読取を認める。 |
| 正規受信箱のエイリアス | 別名のアドレス。実体は 1 つの正規受信箱に届く。 | 独立した取得元として重複取得しない。承認済みの共有受信箱・アドレス・取得元・コネクターと検証済み配送先が一致する場合だけ扱う。 |
| Google グループのアーカイブ・配信アドレス | 配信先メールボックスとアーカイブは異なる取得元になりうる。 | 委員会共有として正確な取得元と配送先を承認できたものだけを対象にする。グループ所属、配信メンバー、To/Cc による推定では対象へ追加しない。 |

### 方針

| ID | 方針 |
| --- | --- |
| MB-01 | `committee-shared` と分類した受信箱だけを、運用者承認済みの `mailboxId`・`address`・`sourceKey`・`connectorId` の組で許可する。To/Cc/Bcc、差出人、ドメイン、所有者の取得能力から追加しない。 |
| MB-02 | 実対象の分類・承認・取得経路・配送証跡は既存の権限の範囲で Git の外に保管する。ヘッダー候補の件数や列挙だけで承認済み対象リストとみなさない。実アドレス・個人名・認証情報をリポジトリに置かない。 |
| MB-03 | 正規受信箱を 1 回だけ取得し、Receipt の冪等キーと Message の共有条件を維持する。各 Receipt の取得元・コネクター・`deliveredTo` が承認済みの組と一致することを検査する。 |
| MB-04 | 個人・未分類・未承認の受信箱は、既存の read Grant があっても委員会共有の経路では取得・表示しない。共有と個人の配送証跡が混在する受信も拒否する。 |
| MB-05 | `LoginService.authenticate` の新しい資格確認後に発行する要求内の会員根拠だけを使う。利用者・会員状態が現在も有効かを読取ごとに検査する。JSON の会員フラグ、プロキシの本人名、デモのペルソナだけでは成立しない。 |
| MB-06 | 全読取導線で Receipt を検査してから検索・件数・スレッド・詳細・添付を作る。未承認の取得元は fetch 前に除外し、反映時にも再検査する。編集は従来の Grant に従い、担当付与で権限を増やさない。 |
| MB-07 | グループ・アカウント認証は検証済み会員根拠を使える。デモの例外は、ループバックで明示した匿名の合成 fixture に限る。`.example` / `.invalid` の固定対象リストを実アドレスへ流用しない。 |
| MB-08 | 承認済み共有メールの本文・添付を部署で制限しない。宛先の画面表示や配送メタデータの非公開は、Receipt の配送先検査と独立して扱う。Bcc を推定して表示しない。 |

## 合成データ

- 人物は「編集担当A」などの役割名、アドレスは `.example` / `.invalid` だけを使う。
- 本文には合成データである旨を記載する。危険な HTML の検証用メールも合成で、通信先はすべて `.example`。
- 現役委員の合成 fixture A〜D は、部署を問わず共有3受信箱すべての本文・添付を閲覧する。
  編集は A がサポート・営業、C が請求だけ。B・D は編集不可。担当候補の従来の Grant 条件も維持する。
- デモ管理者は非会員 fixture で、メール読取は 403。管理・同期の既存権限は別に扱う。
- 固定対象リストは共有スコープと `mailboxId`・`address`・`sourceKey`・`connectorId` を明示する。
  会員根拠の合成例外はループバックで明示したこの fixture だけに適用する。

実メール接続、認証情報の作成、転送設定、API 費用、アクセス権追加、他者招待、本番稼働、
外部送信・自動返信は、対象と影響を示して明示的な承認を得るまで行わない。
LINE の手動返信は機能として承認されたが、実際の送信（チャネル・トークン・費用・受け取り経路）は LN01〜LN09 の承認後。自動返信・一斉送信は対象外。
DNS・TLS 証明書・認証領域・ネットワーク・コンテナの配備も同様（手順書の承認 A1〜A6）。外部からのイメージ・パッケージの取得は承認 A7 として取得ごとに承認を得る。
