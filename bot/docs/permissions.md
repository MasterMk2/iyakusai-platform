# Bot の権限（操作の種類ごとの表）と監査ログ

2026-11-03 追加。Bot の命令を「読む・書く・投稿・配布・起草・管理」の 4 つの種類に分け、Discord のロールで許す表を設定ファイルの 1 か所に持てるようにした。あわせて、書き込みのある命令の監査ログと、Bot が作るファイルへの【AI】の接頭辞と置き先の検査を入れた。
設計と、ほかの選択肢（ロール ID の判定、ドライブとの同期の見直し、契約）は [permissions-design.md](permissions-design.md) を読む。

## 1. 何ができるか

| 機能 | 中身 | 既定（設定が無いとき） |
|---|---|---|
| 操作の種類の表 | 命令ごとに種類（読む・書く・投稿・配布・起草・管理）を決め、種類ごとに許すロールを書く | 全部許可（今と同じ） |
| 入口の確かめ | スラッシュコマンド・`/todo`・候補のボタン・統合アプリの依頼のすべてで、表をサーバー側で確かめる（画面を隠すだけではない） | 全部許可 |
| 拒否の返事 | 拒否されたとき、本人にだけ「この操作（投稿・配布・起草）は、あなたの役割では許可されていません。役員に確かめてください。」と返す。役割の名前は出さない | — |
| 監査ログ | 受付・拒否は入口で、完了・失敗は書き込みのある命令の終わりで、1 行ずつ残す（§4） | 有効（ホストのローカルに書く） |
| 書き込みのガード | Bot が作る文書・画像の名前の先頭に【AI】を付ける。統合アプリの生成物は決めた置き場の中にだけ書く | 有効 |
| 起動時の確認 | 表のロール名のうち、サーバーに無いものをログに出す | 有効 |
| /help の注記 | 表で絞っている操作があるときだけ、/help に「役割により使えない操作があります」と種類の名前を出す | 出ない |

## 2. 操作の種類と命令

命令の名前は監査ログの `cmd` にそのまま入る。表に無い命令は、表の内容に関係なく `admin_roles` の人だけが使える（綴りの誤りや、後から足した命令で全員に開かないため）。

| 種類 | 命令（Discord の名前 → 命令） |
|---|---|
| 読む（read） | `/ask`・`/usage`・`/remind list`・`/haiku check`・`/haiku list`・`/haiku ranking`・`/persona show`・`/todo list`・`/todo show`・`/todo history`・統合アプリの ask |
| 書く（write） | `/remind add`・`/remind done`・`/remind delete`・`/haiku optout`・`/haiku optin`・`/todo`（作成・変更の命令）・週1回のタスク一覧の「引き受ける」ボタン（`todo.weekly_assign`）・候補の承認・却下・取り消し・差し戻し・`/ネタ動画キャンセル`・統合アプリの remind と screening |
| 投稿・配布・起草（send） | `/doc`・`/mail`・`/image`・`/ネタ動画`・統合アプリの doc と image |
| 管理（admin） | `/persona set`・`/persona off`・`/haiku scan` |

- `/help`・`/todo help` は表の対象外（何も変えない）。
- 既存の確かめ（例：`/remind done` は登録者・対象者・役員、`/persona set` は「サーバー管理」権限）は、そのまま残る。表は**追加の確かめ**で、既存の確かめを弱めない。
- `/doc`・`/mail` は草案を依頼者に返すだけで、Bot は送信しない。種類の名前を「投稿・配布・起草」にしたのは、委員会の外へ出る文書を作る操作だから。
- 表で絞っても、Discord のスラッシュメニューと `/help` には全員に出る。使えない役割の人が実行すると、本人にだけ拒否の返事が出る。
- 統合アプリの Bot タブも、入口は全員に出たままになる。依頼すると、拒否の文面（「あなたの役割では許可されていません」）が失敗の理由として画面に出る。依頼者ごとに入口を畳むことは未実装（§7）。

## 3. 表の書き方（設定）

`config.toml` の `[permissions]` に書く。書かなければ何も変わらない（全部許可・監査のみ）。

```toml
[permissions]
admin_roles = ["役員", "システム課"]     # 既存の設定。表で絞った操作は、この役割の人が必ず通る
audit = true                             # 監査ログを書く（既定 true）
# audit_dir = "/home/<user>/.iyakusai/audit"   # 既定は ~/.iyakusai/audit。共有データの外の絶対パス

[permissions.roles]
# 種類ごとに、許すロール名の一覧を書く。書かない種類は全員が使える（コメントを外すと有効）
# send  = ["広報係", "担当委員"]          # 投稿・配布・起草（/doc・/mail・/image・/ネタ動画）
# admin = []                               # [] は admin_roles の人だけ
# read  = ["*"]                            # "*" は全員（明示したいとき）
```

規則:

| 書き方 | 意味 |
|---|---|
| 種類を書かない | 全員が使える（既定） |
| `["ロール名", ...]` | そのロールの人と `admin_roles` の人が使える |
| `[]` | `admin_roles` の人だけ使える |
| `["*"]` | 全員（書かないのと同じだが、明示できる） |
| 種類の綴りを間違える（例：`wirte`） | 起動が止まる（黙って開けない） |
| `admin_roles` や一覧を文字列で書く（例：`"役員"`） | 起動が止まる。文字列を一文字ずつに割ると、管理者の例外が効かなくなるため |
| ロール名の綴りを間違える | 一致しないので、その役割の人は拒否される。起動のログに「権限の表にあるがサーバーに無いロール名」と出る |
| 表に無い命令 | 表の内容に関係なく `admin_roles` の人だけ（閉じる側に倒す） |

- `admin_roles` は既存の設定。表で絞った操作を、この役割の人は必ず通る。
- 役員の判定（Discord の「サーバー管理」権限）は、今も `/persona set` などで使っている。表の `admin_roles` とは別。
- ロール名は、ロールの管理の権限を持つ人が変えられる。変えたら、表の名前も直す。
- 以前に `admin_roles = "役員"` のように文字列で書いていた場合は、今回の変更で起動が止まる。一覧（`["役員"]`）に直してから起動する。

### 有効にする手順

1. `config.toml` に `[permissions]`（必要なら `[permissions.roles]`）を書く。
2. Bot を再起動する（設定は起動のときに読む）。
3. 起動のログに「権限の表にあるがサーバーに無いロール名」が出ていないか確かめる。
4. 試す: 表で絞った種類を、絞られていない人で実行し、拒否の返事が本人にだけ出ることを確かめる。監査ログに `denied` の行が出ることを確かめる。

戻すには、`[permissions.roles]` の行を消して再起動する（表が無ければ全部許可に戻る）。

## 4. 監査ログ

### 置き場所

- 既定は `~/.iyakusai/audit/audit.jsonl`（ホストのローカル）。共有ドライブ（`data_dir`・`knowledge_dir`）とミラーの中には置けない（起動時に検査し、重なれば起動を止める）。
- 1 ファイルが 1 MB を超えたら `audit.jsonl.1` へ回し、5 世代まで残して古いものを消す。
- 書けないとき（ディスクの障害など）は、操作を止めずに警告をログに出す。

### 1 行の形

```json
{"ts":"2026-11-03T10:00:00+09:00","cmd":"todo.create","kind":"write","actor":900000000000000001,"guild":900000000000000010,"channel":900000000000000020,"result":"accepted","code":null,"ref":null}
```

| 列 | 中身 | 例 |
|---|---|---|
| `ts` | 日本時間の時刻（秒まで） | `2026-11-03T10:00:00+09:00` |
| `cmd` | 命令の名前（§2 の名前だけ） | `todo.create` |
| `kind` | 操作の種類 | `write` |
| `actor` | 依頼した人の Discord の数値 ID | `900000000000000001` |
| `guild` / `channel` | サーバーとチャンネルの数値 ID（無ければ null） | — |
| `result` | `accepted`（受付）・`denied`（拒否）・`ok`（完了）・`failed`（失敗） | `denied` |
| `code` | 失敗・拒否の理由の短い記号（大文字）。無ければ null | `FORBIDDEN` |
| `ref` | 対象の番号（数値だけ。無ければ null）。今は使っていない | — |

### 記録する範囲

| 命令の種類 | 受付（accepted） | 拒否（denied） | 完了（ok）・失敗（failed） |
|---|---|---|---|
| 読む（read） | 残さない | 残す | 残さない |
| 書く・投稿・配布・起草・管理 | 残す | 残す | 残す |

- 完了・失敗を残す命令：`/doc`・`/mail`・`/image`・`/ネタ動画`・`/ネタ動画キャンセル`・`/remind add`・`/remind done`・`/remind delete`・`/persona set`・`/persona off`・`/haiku optout`・`/haiku optin`・`/todo` の変更の命令・週1回のタスク一覧の「引き受ける」ボタン・候補のボタン（承認・却下・取り消し・差し戻し）・統合アプリの依頼（remind・screening・doc・image）。
- `code` は失敗の理由の記号（例：`NOT_FOUND`・`VALIDATION`・`FORBIDDEN`・`AI_ERROR`・`INTERNAL`）。本文や例外の文面は書かない。
- 統合アプリの依頼が拒否されたときは、`denied` の 1 行だけを残す（完了の失敗は重ねない）。依頼の失敗の理由は、依頼の結果（ジョブ）に残る。
- 残さないもの：Bot が自分で行う処理（候補の自動起票・リマインドの通知と催促・俳句の検出と投稿・共有チャンネルへの定期の投稿）。委員の命令ではないため、監査の対象外（§7）。
- `accepted` は「受け付けた」の意味で、処理の成否ではない。

### 書かないもの

本文・表示名・メールアドレス・ファイル名・資料の抜粋・タスクの文面。列の検査で、これ以外の値は作れず、規則に合わない行は書かれない。

読み方の例（ホストで）：

```sh
grep '"result":"denied"' ~/.iyakusai/audit/audit.jsonl
```

## 5. 書き込みのガード（【AI】）

- Bot が作る文書（`/ask`・`/doc`・`/mail` の docx・md・txt）・画像（`/image` の PNG と SVG）・統合アプリの生成物の名前の先頭に **【AI】** を付ける。既に付いていれば付けない。
- フォルダの区切り（`/`・`\`）より前の部分は捨て、最後の名前だけを使う。Windows で使えない記号は `_` にする。拡張子は残す。長い名前は 180 字に切る。
- 統合アプリの生成物は、設定の `files_dir` の中にだけ書く（`..` やシンボリックリンクで外へ出る名前は書かない）。同じ依頼の中で同じ名前になったときは、番号（`2-`）を接頭辞の後ろに付けて別の名前にする。
- 例外：共有ドライブの `_目録` の中に Bot が書く出力（候補の日次報告・判定記録など）は、`_目録` が AI 生成のエリアであるため接頭辞を付けない（設計書 §1-2）。

## 6. 試験

- 試験の内容（`bot/tests/`）: 表の解決（既定・上書き・不明なロール・表に無い命令・`admin_roles`）、設定の綴りの誤り（起動を止める）、拒否の返事（本人にだけ・役割の名前を出さない）、監査の列（自由な文字が入らない）・回転・書けないときの扱い、完了と失敗の書き方（命令の本体の分岐）、拒否の確かめが各コマンドに付いていること、命令の名前が表と食い違わないこと、【AI】の接頭辞と置き先の検査、統合アプリの依頼の拒否と監査、生成物の名前の重複。
- 試験の件数（2026-11-03、Python 3.13、discord.py 2.7.1、`python -m unittest discover -s tests`）：334 件中 330 件が合格し、4 件は環境で飛ばした。参照試験（`reference-tests`）は 62 件中 61 件が合格し、1 件（`test_export_tsv`）は Windows に `fcntl` が無いため失敗する（今回の変更の前からの既知の失敗）。
- 環境で飛ばした 4 件：フォントの指定（`IYAKUSAI_TEST_FONT_DIR`）と画像の変換の部品が要る 2 件（`test_images`）、シンボリックリンクを作れない環境の 2 件（`test_access`・`test_assistant_gateway`）。
- 統合アプリ（`app/`）は今回の変更で差分が無い。

## 7. 残り（未実装・委員会の判断が要るもの）

- 表の初期値（どの操作を誰に絞るか）。提案は設計書 §3。今は全部許可のまま。
- ロールの ID での判定（今はロール名。名前は変えられる）。
- 依頼者ごとの入口の表示（統合アプリの Bot タブと、/help の個人別の表示）。今は入口は全員に出て、実行したときに拒否される。
- 個人ごとの回数上限（`/ask`・`/doc`・`/mail` は上限なし）。
- 回答の中の URL の展開の抑止（資料の内容を URL に載せられると外へ漏れうる）。
- 通常の検索（`/ask` の一回の回答・`/doc`・`/mail`）の伏せ字の層（設計書 §1-1・§2）。
- 収集と編集の記録の書き込み先（共有ドライブに直接書いている）。
- 外へ出す操作の人の確認（確認ボタン）。チャンネルへの投稿（統合アプリの共有チャンネルへの投稿を含む）は確認なし。
- Bot が自分で行う処理（候補の自動起票・リマインドの通知・俳句の投稿）の監査。
- フォルダごとの読み書きの許可リスト（提案は設計書 §3）。
- 鍵・トークンの入れ替えの手順。
- 監査ログの閲覧の画面（今はファイルを直接読む）。
