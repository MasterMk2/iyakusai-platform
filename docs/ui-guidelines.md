# 画面設計の方針

統合アプリのタスク・物品貸出・メール・連絡先・Bot・設定を、1 つの業務の道具として使えるようにするための、画面の共通の決まりです。
新しい画面を足すときは §8 のチェックリストを通してください。節の番号はソースのコメントから参照しているので、変えないでください。

## 1. 前提（どう使われるか）

- 学園祭の当日：本部の机で、立ったままスマホを片手で持って使う。屋外で日差しがある。Wi-Fi は途切れる。物品は団体ごとに 10〜30 個を続けて読み取る。
- 準備の期間：PC とスマホでタスクを確かめ、更新する。
- 利用者は委員 30 人前後。操作を覚える時間はほとんどない。

## 2. 共通の枠（ヘッダーと機能タブ）

| 決めたこと | 理由・出典 |
|---|---|
| どの画面も、ヘッダー「医薬祭 委員会アプリ」と機能タブ（ホーム・タスク・物品貸出・メール・連絡先・Bot・設定）で始める。Bot タブは機能が使えないときも出し、使えない理由を Bot の画面に書く。7 つのタブが幅 320px のスマホでも 1 行に収まるよう、340px 以下ではタブの左右の余白を 0 にする。物品画面（`app/src/rental-web/index.html`）も同じ形を HTML で持つ | 機能が変わっても見た目と操作が変わらない。繰り返し出るナビは同じ順序（WCAG 3.2.3）・同じ名前（WCAG 3.2.4） |
| 現在の機能は太字と下線で示し、`aria-current="page"` を付ける | 現在地を示す（WCAG 2.4.8）。色だけで示さない（WCAG 1.4.1） |
| タブは常に表示する。メニュー（≡）に隠さない | 隠すとナビの利用が 44%、見えていると 89%（NN/g） |
| 使えない機能のタブは出さない（物品は `rental.loan` か `rental.issue` を持つ人だけ、メールは受信箱をつないだときだけ） | 押しても何もできない入口を置かない |
| スマホではタブを画面の幅で等分し、アイコンと短いラベル（14px）を出す。ラベルは省かない | ラベルは必須で 1〜2 語（Material 3 のナビゲーションバー） |
| **タブは画面の上に置く**（下ではない） | デジタル庁デザインシステム（DADS）は 2026-09 にボトムナビゲーションを非推奨にした（ブラウザの操作部やジェスチャーと競合し、キーボード・読み上げで届きにくい）。Material 3・Apple はスマホの主なナビを下に置くことを勧めるが、物品画面では「撮って登録・次へ」「異常なしで返却・次へ」など主な操作が画面の下側にあり、続けて読み取っている最中にタブを誤って押すと送信が止まる。iPhone の Safari の下のツールバーとも重なる。機能の切り替えは機能の中の操作よりずっと少ないので、届きやすさより誤操作の防止を選んだ。主な操作を中央、副次的な操作を上下の端に置く（Hoober 2017） |
| 物品画面を離れるとき、未送信の登録があれば確認を出す | 未送信は端末に残るが、送信は物品画面を開いているあいだしか進まない。確認は未送信があるときだけ出す（多用すると読まれなくなる：NN/g） |
| ブラウザのタブの名前は「機能名｜医薬祭 委員会アプリ」 | 履歴やタブの一覧で、いまどこかが分かる |

## 3. ホーム（いま対応が必要なもの）

- 開いたときの最初の画面。機能ごとにカードを 1 枚置き、**対応が必要な数だけ**を出す。全体の量や飾りの数字は出さない（業務のダッシュボードは「許容範囲を外れた値に気づかせる」ためのもの：NN/g）。
  - 物品貸出：貸出中（件数・団体数）、要確認（整備・破損で返却）、貸し出せる数。返却待ちの団体（いつから）、要確認の物品。データは `GET /api/rental/summary`。
  - タスク：未完了の合計、部署別の残り・期限超過・今日まで、期限の区分別と日付別の残り。部署の名前から未完了の一覧へ。データは `GET /api/tasks/summary`（タスク API の署名付きの集計を 1 回だけ呼ぶ）。課は所属する部に含め、複数の部署に付いたタスクも合計では 1 件と数える。
  - メール：未対応の件数（受信箱をつないだとき）。
  - Bot：承認待ちのタスク候補の件数と、自分のリマインドの期限超過・今日まで。データは `GET /api/assistant/summary`（1 回）。Bot が無効のときと、委員の登録がない人には出さない。
- 取れなかった数は 0 件と書かない。エラーと再試行を出す。再取得に失敗したときは、前回の件数であることを示す。
- 数に色を付けるのは注意が要るときだけ（期限超過・未対応は赤、要確認・今日までは黄）。0 件のときは色を付けない。済んだものを目立たせない（GOV.UK のタスクリスト）。
- カードごとに機能へのボタンを 1 つ（物品は「貸出・返却を始める」）。
- **外部を何度も呼ばない**：タスクの正本はタスク API で、要求のたびに Discord の権限を問い合わせる。ホームのために委員会ごとに一覧を要求すると、Discord の回数の制限にかかってタスクの画面まで使えなくなる。ホームの件数は、タスク API の集計の口（閲覧の権限を確かめてから DB を 1 回読み、部署別・期限別の件数だけを返す）から取る。

## 4. 状態と色（全機能で同じ意味）

| 意味 | 色（文字／背景） | 使う場面 |
|---|---|---|
| すぐ対応 | 赤 `#a32830`／`#ffecef` | 期限超過、メールの未対応、送信の失敗、エラー |
| 注意 | 黄 `#865006`／`#fff0cf` | 要確認（整備・破損）、保留、今日まで、未送信 |
| 動いている | 紺・青 `#163960`／`#e7f0fc` | 進行中、貸出中、読み込み中、お知らせ |
| 済み | 緑 `#126744`／`#dcefe6` | 完了、送信済み、保存しました |
| なし | 墨 `#172c40`／`#edf2f7` | 未着手、貸出可 |

- タスクの状態の札（未着手・進行中・保留・完了）は一覧に並ぶので、同じ系統の枠を付ける（未着手 `#7a8d9f`、進行中 `#075fd0`、保留 `#d99b28`、完了 `#6fb08f`）。進行中だけは地を `#cfe1fa` に濃くする。表の `#e7f0fc` のままだと、未着手の地 `#edf2f7` と選ばれた行の地にほぼ重なり、見分けられないため。文字と地のコントラストは 12.7／8.8／5.9／5.7:1（計算値）。札は押せないので、枠は飾りとして 3:1 の対象にしない。
- 色だけで伝えない。状態には必ず文字を付ける（WCAG 1.4.1。GOV.UK のタグ、Carbon の状態表示も同じ）。
- コントラスト：文字は 4.5:1 以上（WCAG 1.4.3）、入力欄の枠などの部品は 3:1 以上（WCAG 1.4.11）。上の表の組み合わせは 5.7〜12.7:1、補足の文字（`#52677b`）は白地で 5.9:1・薄い地で 5.4:1（計算値）。入力欄の枠は `#7a8d9f`（白地で 3.4:1）。区切り線（`#ccd7e1`）は飾りなので対象外。屋外での見やすさの公式な数値は見つからなかったので、目安として 7:1（WCAG 1.4.6、AAA）に近い濃い文字色を使う。
- 状態の札は押せないものにする。押せるのはボタンとリンクだけ。
- 上の色の値はライトのテーマのもの。若葉・ダークのテーマの値は `app/src/client/styles.css` にある。

## 5. 大きさと文字

- 色・文字・大きさの値は、`app/src/client/styles.css` と `app/src/rental-web/styles.css` の先頭（`:root`）に同じものを置く。片方を変えたら、もう片方も変える。
- タッチの端末（`pointer: coarse`）では、ボタン・入力欄・選択欄を高さ 44px 以上にする（WCAG 2.5.5、Apple HIG）。どうしても小さいもの（札の × など）も 24px 以上（WCAG 2.5.8）。タブは 48〜56px。
- 文字：本文と入力欄は 16px、行間は 1.6（DADS は本文 160〜175%）。補足・一覧の付記・札・スマホのタブのラベルも含めて **14px 未満にしない**（DADS：本文と UI は 16px 以上、14px は領域が限られる場合だけ、14px 未満は原則認めない）。入力欄を 16px にするのは、iPhone が入力のときに拡大しないようにするため（開発者の経験則。Apple の公式の文書では確かめていない）。
- 物品画面（`app/src/rental-web/styles.css`）の中身には、12〜13px の文字がまだ残っている（読み取り待ちの一覧の状態など）。共通の枠（ヘッダー・タブ）と入力欄の枠・フォーカスの表示だけをそろえてある（§9）。
- 拡大（ピンチズーム）を禁止しない（WCAG 1.4.4）。
- 書体：`'Yu Gothic UI', 'Hiragino Sans', 'Hiragino Kaku Gothic ProN', 'Noto Sans JP', Meiryo, sans-serif`（Windows・iPhone・Android の日本語の書体を順に）。`system-ui` は先頭に置かない（Windows で中国語の書体が選ばれた報告がある：CSSWG issue #3658）。Android は `lang="ja"` で日本語の Noto Sans CJK が選ばれるので、HTML の `lang` を必ず付ける。
- キーボードの操作の位置（フォーカス）は「黒の枠と黄の縁」（黒 3px と `#ffd43d` 2px）で示す。どの背景（白・紺のヘッダー）でも見える（DADS と同じ考え方）。薄い青の枠は白地で 2.3:1 しかなく、見えにくい。
- 上に貼り付くタブにフォーカスした部品が隠れないよう、`scroll-padding-top` を空ける（WCAG 2.4.11）。
- 目標の水準は WCAG 2.2 の AA（総務省「みんなの公共サイト運用ガイドライン」2024 年版が公的機関に求める水準。JIS X 8341-3:2016 は WCAG 2.0 と同じ内容）。

## 6. 画面の幅

| 幅 | 形 |
|---|---|
| 901px 以上（PC） | メールは 3 列（受信箱の一覧・スレッドの一覧・詳細）、タスクは 2 列（一覧・詳細） |
| 900px 以下 | 1 列。一覧 → 押すと詳細だけ → 上の「← 一覧に戻る」で一覧へ（横のスクロールを出さない） |
| 680px 以下（スマホ） | タブを等分・縦並び（アイコンの下にラベル）、余白を詰める、入力欄は幅いっぱい |

## 7. 入力・確認・エラー

- ラベルは入力欄の上に書く。プレースホルダー（薄い例文）をラベルの代わりにしない（GOV.UK、NN/g）。
- エラーは起きた場所の近くに、何が起きたか・どうすればよいかを書く。入力した内容は消さない。
- 確認のダイアログは、取り消せない・影響が大きい操作のときだけ出す。ボタンの文言は結果で書く（「移動する」「とどまる」など）。物品画面の確認はブラウザの標準の確認（OK／キャンセル）なので、文面の最後を「移動しますか？」にしている。
- 主なボタンは 1 画面に 1 つ（物品のカードの「貸出・返却を始める」など）。

## 8. 新しい画面・機能を足すときのチェックリスト

- [ ] ヘッダーと機能タブの中に置いたか。タブの順序・名前を変えていないか（変えるなら物品画面の HTML も同時に）
- [ ] スマホの幅（375px）で横のスクロールが出ないか。一覧と詳細は 1 列で切り替わるか
- [ ] 状態に文字を付けたか。色は §4 の意味どおりか
- [ ] 押せる部品は、スマホで 44px 以上あるか
- [ ] ホームに出すべき「対応が必要な数」はあるか（あればカードを足す）。ただし 1 回の表示で外部（タスク API など）を何度も呼ばない。タスク API は 1 画面あたり数件まで
- [ ] 運用に出す前に、運用と同じ量のデータ（委員会の数・物品の数）で要求の回数を数えたか
- [ ] 権限がない人に入口を見せていないか

## 9. 見送ったこと・次の候補

- 物品の読み取りの成功・失敗を、音と振動で知らせる（Material のバーコードの読み取りの指針、Apple の触覚）。iPhone の Safari は振動に対応していない。
- 物品画面の中身の文字を 14px 以上にそろえる。
- ホームの「自分のタスク」の件数（未完了・期限超過・今日まで）。タスク API に、全委員会の自分の担当を 1 回で返す口を足すか、Discord の権限を短い時間だけ覚えるようにしてから。
- 物品の一覧の画面（PC は表、スマホはカード）。物品画面の「情報」タブ（`/api/rental/overview`）とホームの集計（`/api/rental/summary`）を一本にするかも考える。
- 物品画面のタブにメールを出す。いまの物品画面のタブは固定。
- 物品画面の確認を独自の画面にして、ボタンを「移動する」「とどまる」にする。
- タスクの詳細の「項目ごとの保存ボタン」（変更するまで押せない）。押せないボタンは理由が分かりにくい（GOV.UK、NN/g）。まとめて保存する形にするかは、Discord の `/todo` と同じ版の管理なので別に考える。
