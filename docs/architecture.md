# 全体の構成

委員会の運営に使う部品と、そのつながりをまとめます。部品ごとの細かい設計は各ディレクトリの文書にあります。

## 1. 使われ方

- 利用者は委員 30 人前後。準備期間は PC とスマホでタスクとメールを見る。学園祭の当日は、本部でスマホを片手に物品を貸し出し、返却を受け付ける。
- 委員会の連絡の中心は Discord。決まったこと・依頼・質問は Discord に集まるので、タスクとリマインドも Discord から扱えるようにしている。
- 対外の窓口は、委員会のメール（Google Workspace のグループ）と LINE 公式アカウント。

## 2. 部品

```text
            ブラウザ（委員のスマホ・PC）
                 │ HTTPS
                 ▼
          リバースプロキシ ──────────────┐
                 │                       │ 物品カードの URL（/i/<個体コード>）
                 ▼                       ▼
   ┌──────── 統合アプリ（app/） ────────────────────┐
   │ ログイン / タスク画面 / 物品貸出 / メール /    │
   │ 連絡先 / Bot タブ / 設定                       │
   │ 保存: アカウント（JSON）・物品（SQLite＋写真）・│
   │       メール（SQLite＋添付）・連絡先（SQLite）  │
   └──┬──────────────┬────────────────┬────────────┘
      │署名付き       │署名付き          ▲署名付き
      ▼              ▼                 │
 タスク API      登録（bot/registration/）  GAS（Gmail → メールの取り込み、
 （bot/gateway/）  委員の確認・登録コードの DM   物品の記録 → Google ドライブ）
      │
      ▼
 タスク DB（SQLite）◀── IyakusaiBot（bot/src/）──▶ Discord
                         │  ▲
                         │  └─ Bot のデータソース（統合アプリから物品・受信箱の状態を読む）
                         ▼
                   委員会の資料（共有ドライブの写し）を検索して /ask に答える

 collectors/line-oa/  … LINE 公式アカウントの Webhook の受け口と取り込み
 collectors/line-oa-relay/ … 受け取った LINE を Discord のフォーラムへ転送
```

| 部品 | 動く場所 | 役割 |
|---|---|---|
| 統合アプリ（`app/`） | コンテナ 1 つ（Node.js 22） | 委員が使う画面のすべて。タスクは保存せず、タスク API を呼ぶ |
| 物品の発行・読取ソフト（`app/clients/`） | 委員会の Windows PC | NFC カード（読取機 RC-S370）への書き込みと、カードを置いたときにブラウザの物品画面へ渡す読取り |
| IyakusaiBot（`bot/src/`） | Bot ホスト（Linux。Windows でも動く） | Discord のコマンド（`/ask`・`/doc`・`/remind`・`/todo` など）、タスク候補の抽出、統合アプリの Bot タブの処理 |
| タスク API（`bot/gateway/`） | Bot ホスト（Bot と同じタスク DB を読む） | 統合アプリからのタスクの読み書き。TLS と署名と接続元の制限つき |
| 登録（`bot/registration/`） | Bot ホスト（Bot のプロセスの中） | Discord の `/register` と、ログイン用の登録コードの DM |
| GAS（`gas/`・`app/deploy/unified/gas/`） | Google Apps Script（委員会のアカウント） | メールの保存・統合アプリへの送り込み、物品の記録のドライブへの複製 |
| 収集（`collectors/`） | Bot ホスト | Discord と LINE 公式アカウントの記録 |

## 3. データの正本

| データ | 正本 | ほかの部品からの見え方 |
|---|---|---|
| タスク | Bot ホストのタスク DB（SQLite） | Discord の `/todo` と統合アプリのタスク画面は、同じタスク・同じ版・同じ履歴を操作する。統合アプリはタスクを保存しない |
| 物品の台帳と写真 | 統合アプリの SQLite と写真のフォルダ | GAS が署名付きで取りに来て、Google ドライブに写真・記録・一覧を複製する |
| 委員会のメール | Gmail | GAS が元のメール（RFC 5322）を 1 通ずつ統合アプリへ送る。統合アプリから Gmail へは書き込まない（送信だけは SMTP で別に行う） |
| LINE 公式アカウントの会話 | 受け口（`collectors/line-oa/`）の保存 | 統合アプリと Discord への転送は、受け口の書き出しを読む |
| アカウント | 統合アプリのアカウントのファイル | パスワードは scrypt、コードとセッションはハッシュだけを保存する |
| 委員会の資料 | 共有ドライブ | Bot は、機微な行を伏せた写し（ミラー）だけを読む |

## 4. 部品の間の呼び出し（svc-auth/v1）

部品の間の HTTP 呼び出しは、すべて同じ形式で署名します。

- 正規文字列：版（`svc-auth/v1`）・クライアント ID・メソッド・パス（クエリを含む）・時刻・nonce・利用者（actor）・本文の SHA-256 を改行でつないだもの。これを HMAC-SHA256 で署名する。
- ヘッダー：`x-svc-client`・`x-svc-timestamp`・`x-svc-nonce`・`x-svc-actor`・`x-svc-signature`。
- 時刻のずれは前後 30 秒まで。nonce は 1 回だけ使える。鍵は 32 バイト以上。
- 鍵は呼び出しの経路ごとに別にする（タスク連携・登録・メールの取り込み・物品の複製・Bot のデータソース）。統合アプリは、別の経路の鍵と同じ値を見つけると起動を止める。漏れたときの影響を、その経路だけに閉じるため。
- ブラウザは鍵を持たない。統合アプリが、ログインを確かめた利用者を actor として署名するので、ブラウザから利用者を偽ることはできない。

実装は `app/src/server/tasks/signing.ts`（統合アプリ）と `bot/gateway/bot_task_gateway.py`（タスク API）。経路ごとの取り決めは次の文書にあります。

- タスク：[`app/docs/task-service/integration-api.md`](../app/docs/task-service/integration-api.md)
- 共通入口とアカウント：[`app/docs/unified-integration.md`](../app/docs/unified-integration.md)
- Bot タブ：[docs/contracts/bot-front.md](contracts/bot-front.md)
- Bot のデータソース：[docs/contracts/bot-datasource.md](contracts/bot-datasource.md)
- メールの取り込み：[docs/mail.md](mail.md)

## 5. ログイン

運用では `SMM_AUTH_MODE=discord` で動かします。

1. 委員は Discord で `/register` を実行する。Bot ホストの登録の仕組みが統合アプリに 1 回限りのコードの発行を頼み、そのコードを DM で届ける。
2. 委員は統合アプリでコードを入れ、パスワードを決める。ログインの ID は学籍番号（運用者の名簿で、はじめから学籍番号で入れるようにもできる）。
3. 以後は学籍番号とパスワードでログインする。ログインはその端末で 14 日保つ。メールの画面だけは、最後に使ってから 12 時間を過ぎるとパスワードを入れ直す。
4. 登録・ログイン・パスワードの変更のたびに、委員会の Discord サーバーにまだ参加しているかを Bot ホストに確かめる（答えは 10 分だけ使い回す）。抜けた人は使えなくなる。Bot ホストに届かないあいだも、ログイン済みの人は 48 時間まで使える。
5. パスワードの誤りは、10 分に 5 回・24 時間に 15 回までで止める。ログイン・登録・コードの記録は、権限の管理者が見られる。

統合アプリと Bot ホストの登録の仕組みとの呼び出しは、この経路専用の鍵で署名します（統合アプリ → Bot ホスト：委員の確認と DM、Bot ホスト → 統合アプリ：コードの発行）。Bot ホストは自前の CA の TLS で待ち受けます。

ほかに、学園祭の当日だけ使う臨時スタッフのアカウント（物品の作業だけ。番号の範囲は `SMM_TEMPORARY_STAFF_RANGE`）と、委員カード（NFC）でのログインがあります。

合成データで試すための `demo`（ペルソナを選ぶだけ）、`account-mock`（模擬の DM）、前段のプロキシに認証を任せる `trusted-proxy` もあります（[`app/README.md`](../app/README.md)）。

## 6. 権限

- 画面を開けるのは、ログインした委員だけ。
- タスク：Discord の役割（委員会ごとのロール）に従う。Discord の `/todo` と同じ規則。
- 物品：貸出・返却（`rental.loan`）と、カードの発行・台帳の管理（`rental.issue`）を分けている。
- メール：読むのは委員全員。メモの追加・送信は、受信箱ごとに権限の管理者が付けた人だけ（[docs/mail.md](mail.md)）。
- 使えない機能の入口は画面に出さない（[docs/ui-guidelines.md](ui-guidelines.md) §2）。

## 7. 障害のときの考え方

- 統合アプリとタスク API は別のホストで動く。片方が止まっても、もう片方の機能（たとえば物品貸出）は使える。
- 統合アプリは、タスク API から取れなかった件数を 0 件とは表示せず、エラーと再試行を出す。
- 物品画面は、通信が切れても読み取った内容と写真を端末に残し、つながったときに送る。
- それでも使えないときのために、紙の台帳で運用を続けられるようにしている（手順は運用の側で持つ）。
